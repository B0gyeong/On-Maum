# 데이터 레이크 기반 집계·위험 평가·보고서 자동화 통합 설계

- 정리일: 2026-09-20
- 범위: 단일 노드 자동화, Silver/Gold 집계, 분석 완료 증거, 모니터링 위험 평가, 보고서, 분산 테스트
- 성격: 지금까지의 대화·첨부 검토·작업 트리 확인을 종합한 설계 문서
- 구현 상태 표기는 코드 존재 기준이다. 운영 배포·성능·실제 데이터 검증 완료를 뜻하지 않는다.
- 이번 작업은 문서 작성이며 서비스 코드·설정·DB 스키마를 변경하지 않는다.

## 1. 목표와 최종 역할 분담

현재 DB 중심의 집계를 데이터 레이크 중심으로 옮긴다. 레이크를 원본 보관소에 그치지 않고 정제, 관측 품질 관리, 가전별 사용 요약, 통계 프로필, 보고서, 재처리와 모델 검증의 기반으로 사용한다.

핵심 결정은 다음과 같다.

> Spark 배치는 과거 데이터를 정제해 가구별 통계 기준과 요약을 만든다. 모니터링 서비스는 그 기준을 현재 관측값·외출 상태·정책과 비교해 최종 위험 점수, 등급, 알림을 결정한다.

| 영역 | 최종 책임 |
|---|---|
| 원본 수집 | 전력 원본·Kafka 위치·오류 데이터 보존 |
| 실시간 분석 | 가전 상태, 유효 사용 세션, 분석 결과와 품질 근거 생성 |
| Spark 배치 | 정제·중복 제거·파일 병합·관측 품질·사용 요약·통계 프로필 |
| 모니터링 | 현재 위험 평가, 정책 적용, 등급 전환, 알림 |
| 데이터 레이크 | 원본·세션 변경 이력·정제 결과·통계·평가 이력 보존 |
| 서비스 DB | 운영 정보, 최신 프로필·상태, 빠른 조회용 결과, 실행 제어 정보 |
| 보고서 생성 | 확정 통계와 실제 평가 이력으로 결과와 근거 설명 |

DB를 제거하는 설계가 아니다. 회원·가구·기기 등록, 외출 상태, 정책, 알림 처리 같은 즉시 조회·수정 데이터는 DB에 유지한다. 장기간 보존하고 반복 분석할 데이터와 계산 이력은 레이크에 둔다.

## 2. 현재 코드에서 확인한 상태

| 구성 | 확인된 구현 | 남은 작업 |
|---|---|---|
| `bronze-loader` | Kafka 전력 원본 → HDFS Parquet, manifest, 오류 격리 | 레이크 후속 집계와 입력 준비·보존 조건 연결 |
| `session-lake-loader` | 초기 세션 적재, outbox 증분, 수정·삭제, 버전 복원 검증 | Spark 세션 복원·일별 사용 요약 연결 |
| `power-silver-service` | Spark 원본 정제, 중복 제거, 파일 병합, 슬롯 기준 관측일, 버전 카탈로그 | 후속 요약의 버전 고정 입력으로 연결 |
| DB 일일 집계 | 활동지수, 루틴 변화, `routine_baseline` 갱신 | 레이크 결과와 병행 검증 후 전환 |
| 분석 Snapshot | 추론·상태 판정·세션 DB 저장 후 `analysis.snapshot.v1` 발행 | 레이크 보존, 입력과 대응, 분석 증거로 활용 |
| 분석 완료 증거 | 독립적인 일별 완료 계약 없음 | 입력 범위·분석 완료·세션 전달 확인 계약 |
| 모니터링 점수 | 전달받은 `message.score()`를 적용, 기본 70/90으로 등급 구분 | 프로필과 현재 상태로 직접 점수 계산 |
| Gold 프로필·보고서 | 이번 목표 구조 전체는 미구현 | 일별 요약, 시간대 통계, 평가 이력, 보고서 연결 |

주의할 점:

- 앞선 대화에서 “세션 적재와 전력 Silver를 새로 만들어야 한다”고 했던 부분은 현재 작업 트리 기준으로 갱신한다. 두 구성은 이미 코드가 있다.
- `power_silver/commit.py`에는 날짜별 `date_lock`, 오래된 attempt의 활성화 방지 로직이 추가되어 있다. 관련 테스트도 존재한다. 이번 정리는 테스트를 실행해 통과를 확인한 것이 아니다.
- 기존 상세 설계의 완료 증거를 뒤쪽 구현 순서에 둔 부분은 아래 임계 경로 검토에 따라 조정한다.

## 3. 최종 전체 흐름

```text
[상시 수집·분석]
센서 → Kafka ┬→ 전력 수집기 → Bronze power_raw
             └→ 실시간 가전 분석
                   ├→ 세션 DB + outbox → Bronze session changes
                   ├→ analysis.snapshot.v1 → 현재 상태 / 레이크 증거 적재(추가)
                   └→ GAP·RECOVERED → 품질 근거 적재(추가)

[일일 레이크 배치]
전력 Bronze → 검증·중복 제거·파일 병합 → Silver power_clean
                                         └→ Silver household_observation_daily
세션 Bronze → 최신 버전 복원·삭제 반영 → Silver session slices / logical uses
분석 증거 ─────────────────────────────────────┐
Silver 관측일 + 논리 사용 ──────────────────────┴→ Gold 일별 사용 요약
                                                      ├→ routine baseline 이력
                                                      ├→ 시간대별 통계 프로필
                                                      └→ 최근 변화 통계

[위험 평가·보고서]
검증한 Gold 프로필 → 모니터링 최신 프로필
현재 상태·품질·외출·정책 → 모니터링 위험 점수·등급·알림
                                 ↓
                           평가 이력 → 레이크
Gold 통계 + 실제 평가 이력 ─────────→ 일일/주간 보고서
```

실행 주기는 구분한다.

- 수집과 실시간 분석은 계속 실행한다.
- 매일 전날까지의 데이터를 고정해 정제·집계한다. 정해진 시각 도달만으로 입력 완료를 선언하지 않는다.
- 모니터링은 상태 변경 시 평가하고, 입력 이벤트가 없어도 무활동 시간이 증가하므로 타이머로 평가한다.
- 보고서는 대상 기간 데이터와 평가 이력이 준비된 뒤 생성한다. 미완료이면 잠정/지연 상태를 표시한다.

| Bronze | `analysis_snapshots` — 제안 | 입력별 분석 결과, 현재 가전 상태 |

| Silver | `household_observation_daily` | 가구·날짜별 관측 슬롯·수집률·관측 상태 |
| Silver | `appliance_session_daily_slices` — 제안 | 최신 세션을 날짜 경계로 자른 구간 |

| Silver | `analysis_coverage` — 제안 | 입력과 성공 증거를 대응한 분석 커버리지·누락 구간 |

| Gold | `household_statistical_profile` — 제안 | 시간대·요일별 평소 통계 |

모니터링 평가 이력도 원본 평가 이벤트를 먼저 보존하고, 중복 제거·버전 정리 후 보고서용 집계로 연결한다.

“Silver에서 일별 요약 생성”은 Silver 입력을 사용한다는 뜻이다. 집계 결과 자체는 Gold에 두는 것으로 정리한다.
`routine_baseline`만으로 무활동·장시간 사용·같은 시각의 활동 감소를 모두 평가할 수는 없다. 시간대별 프로필이 추가로 필요하다.

## 5. 원본 전력과 사용 세션의 관계

원본 전력으로 직접 계산할 수 있는 것은 수집 품질, 누락, 전체 전력 통계 등이다. 가전별 사용일·첫 사용·사용 지속시간에는 가전 분석 결과가 필요하다.

전체 전력의 소비전력량도 단순 샘플 합계가 아니라 단위와 실제 측정 간격을 반영해야 한다. 가전별 전력 출력이 없다면 가전별 소비전력량을 임의로 산출하지 않는다.

초기 경로는 기존 실시간 분석이 만든 세션 변경 이력을 레이크에서 읽는 방식이다. 후속 경로로 원본을 모델에 다시 입력하는 배치 추론을 구현할 수 있다. 이때 모델 버전, 입력 구간, 윈도우 준비 구간, 결과 버전을 함께 보존한다.

## 6. 원본 정제·파일 병합의 기준

1. 완료 manifest에 있는 입력 파일을 선택한다. 수집일과 측정일을 구분한다.
2. 명시적 스키마로 읽고 ID·시각·숫자·범위를 검증한다.
3. Kafka 위치 중복과 메시지 ID 중복을 구분한다. 같은 키·다른 내용은 충돌로 격리한다.
4. 업무 날짜를 한국 시간으로 계산한다. 실행 노드의 로컬 시간대에 의존하지 않는다.
5. 대표 계측기·적용 기간 설정을 기준으로 기대 관측 슬롯을 만든다.
6. 정상 데이터가 없는 가구도 결과가 생기도록 관측 대상 목록에서 LEFT JOIN한다.
7. 파일 크기와 병합 수는 측정 후 결정한다. 무조건 파일 하나로 만드는 것은 피한다.
8. 임시 결과를 검증하고 버전별 경로·manifest·활성 카탈로그로 공개한다.

Silver의 수집률은 중복 제거한 관측 슬롯 기준이다. DB의 단순 수신 건수 기반 비율과 버스트·중복 상황에서 다를 수 있다.
전력 배치는 입력 준비를 기다리거나 제한 시간 이후 있는 입력으로 확정할 수 있다. 이것은 모든 센서 입력 또는 모든 분석이 완료되었다는 보증이 아니다.

현재 전력 Bronze 보존 정책은 수집일 기준 compaction 완료 마커를 확인한다. 측정일 기준 Silver 완료를 같은 의미로 사용해 원본을 삭제하면 안 된다. 입력 파일별 처리 완료·후속 재현 필요성을 연결한 보존 설계가 선행되어야 한다.

## 7. Silver 입력 기반 일별 가전 사용 요약

### 7.1 최신 세션 복원

복원 순서는 반드시 다음과 같다.

```text
입력 manifest 고정 → 세션·버전별 내용 충돌 검사
→ 동일 내용 중복 제거 → 세션별 최신 버전 선택
→ DELETE 제외 → 실제 구간 기준 날짜 배정
```

- 날짜로 먼저 거르면 이후 수정·삭제 버전을 놓칠 수 있다.
- 최신 버전은 `session_version`으로 선택한다. event ID 최댓값으로 상태를 판정하지 않는다.
- SNAPSHOT과 INSERT의 전달 메타데이터 차이는 충돌이 아니다. 기존 `CONTENT_FIELDS`를 사용한다.
- DELETE에는 가구·가전·부모 관측일이 없을 수 있다. 수정 영향 범위는 이전 살아 있는 상태에서 찾는다.
- tombstone을 보존해 늦게 온 낮은 버전이 삭제 세션을 되살리지 못하게 한다.
- 현재 계약의 모델 버전·가전 개체 ID 부재는 별도 계약 확장 대상이다. 없는 값을 만들어 넣지 않는다.

### 7.2 날짜·논리 사용 규칙

업무 날짜 D의 구간은 `[D 00:00, D+1 00:00)`이며 UTC instant로 변환해 계산한다.

| 규칙 | 정의 |
|---|---|
| 날짜 포함 | 세션이 해당 날짜와 실제로 겹칠 때 |
| 전기포트·전자레인지·드라이어·청소기 병합 | 세션 간격 60초 이하 |
| 인덕션 병합 | 120초 이하 |
| 다리미 병합 | 300초 이하 |
| 유효 사용 | 병합한 세션의 실제 사용시간 합계 10초 이상 |
| 사용시간 | 켜져 있던 세션 길이 합, 병합 사이 꺼진 간격 제외 |
| 경과시간 | 논리 사용 마지막 끝 - 첫 시작; 사용시간과 별도 |
| 첫 사용 | 해당 날짜의 첫 유효 논리 사용 시작 |
| 시작 횟수 | 원래 논리 사용이 해당 날짜에 시작한 경우만 가산 |

Spark는 가구·가전·날짜별로 정렬하고, 이전 모든 세션의 최대 종료시각을 기준으로 그룹 경계를 찾는다. `lag(end)` 하나만 쓰면 포함 관계 세션에서 병합이 틀릴 수 있다.
시간은 정수 마이크로초로 계산하고 마지막에 단위를 변환한다.

경계 정책:

- 전날부터 이어진 유효 사용은 당일 첫 시각이 00:00일 수 있고, 당일 시작 횟수는 0이다.
- 날짜별로 자른 뒤 10초 조건을 적용한다. 자정 양쪽 각각 6초는 두 날 모두 유효 사용이 아니다.
- 미종료 세션은 종료 대체값을 쓴 진단 구간만 남기고 기본 확정 요약은 UNKNOWN으로 한다.
- 서로 다른 세션의 시간 중복은 과대합산 우려가 있어 표시하고 기본 확정 요약에서 제외한다. 합집합 시간 규칙 도입은 별도 버전으로 다룬다.

### 7.3 일별 요약 계약

업무 키: `(usage_date, household_id, appliance_type)`.

주요 필드:

```text
observation_status, coverage_ratio
analysis_status, delivery_status, quality_flags
usage_status, is_used, baseline_eligible
logical_use_count, usage_start_count, usage_duration_us
first_use_at, first_use_second, last_use_end_at
source_session_count, rejected_short_use_count, open_session_count, overlap_count
observation_run_id, analysis_evidence_version
run_id, input_snapshot_id, rule_version, config_version, schema_version
```

품질 마스킹 전 계산값은 shadow 비교 산출물로 보존할 수 있다. 이를 운영용 확정값과 구분한다.

| 상황 | usage_status | is_used | baseline 포함 |
|---|---|---|---|
| 관측·분석·전달 정상 + 유효 사용 있음 | USED | true | 포함 |
| 관측·분석·전달 정상 + 유효 사용 없음 | NOT_USED | false | 포함 |
| 관측 부족·분석 미확인·전달 대기·세션 품질 문제 | UNKNOWN | null | 제외 |
| 적용 대상 아님 | NOT_APPLICABLE | null | 제외 |

NOT_USED는 횟수·시간 0, 시각 null이다. UNKNOWN은 확정 횟수·시간도 null로 두고 진단값을 별도로 제공한다.
v1 제안에서는 `PARTIAL_DAY`를 baseline 표본에서 제외한다. 이는 기존 DB 기준과 다른 정책이므로 병행 비교에서 구분한다.

### 7.4 논리 사용 구간 보존 추가

일별 합계만 저장하면 시간대별 누적 활동, 무활동 공백, 개별 지속시간 분포를 복원하기 어렵다. 병합 결과 `appliance_logical_uses`도 Silver에 보존한다.

필드 제안: 가구·가전·시작·끝·실제 사용시간·경과시간·원천 세션 참조·원래 시작 시각·자정 분할 여부·품질·버전.
날짜별 slice와 원래 사용 episode의 연결을 유지한다. 장시간 사용 분포를 만들 때 날짜별로 잘린 조각을 하나의 완료 세션처럼 취급하지 않는다.
원래 episode의 재구성과 검증이 준비되기 전에는 자정 경계·미종료 사례를 지속시간 학습에서 제외하고 표본 수를 명시한다.

## 8. 분석 완료 증거: 운영 전환의 임계 경로

### 8.1 왜 필요한가

레이크에 사용 세션이 없다는 사실은 정상 미사용, 추론 누락, 세션 전달 지연 모두에서 나타난다.
현재 handler는 관측을 기록한 후 버퍼·품질 게이트를 통과한 경우에만 추론하므로 `관측 VALID = 분석 완료`가 성립하지 않는다.

엄격한 품질 정책에서는 완료 증거 없는 적용 대상 요약이 UNKNOWN이고 baseline 표본이 되지 않는다. 따라서 이 계약은 운영 전환의 선행 조건이다.
세션 복원·병합·산술·저장 검증은 독립적으로 개발할 수 있고, 품질 분기도 주입한 증거로 테스트할 수 있다. 실제 생산자와 전달 경로의 종단 검증이 임계 경로에 남는다.

### 8.2 첨부 검토에서 바로잡은 내용

| 주장 | 코드 검토 결과 |
|---|---|
| 재시작하면 추론 공백 발생 | 맞음. 기본 299개 윈도우에서 첫 298샘플은 추론하지 않음 |
| 120초 + 복구 3초 + 버퍼 299초 | 복구 확인 중에도 버퍼를 채우므로 3초와 299초가 중첩됨. 실제 시간은 수신 속도·watchdog에 의존 |
| GAP은 측정시각 간격으로 판정 | watchdog은 마지막 정상 입력 수신시각부터의 경과시간으로 판정 |
| GAP 이벤트로 추론 공백을 모두 복원 | 불가. 재시작 워밍업·복구 이후 버퍼 충전·추론 실패까지 포괄하지 않음 |
| 새 카운터 외에 증거 재료가 거의 없음 | 기존 `analysis.snapshot.v1`을 활용할 수 있음 |
| ID 최댓값으로 전달 완료 확인 | 불가. ID 할당 순서와 트랜잭션 커밋 순서는 다를 수 있음 |
| 일일 모든 세션 변경과 완료를 한 트랜잭션으로 처리해야 함 | 유일한 방법은 아님. 처리 증거와 변경 기록의 일관성·마감 경계·전달 장벽을 보장해야 함 |

GAP 상태 자체도 메모리에 있으므로 GAP 이벤트 부재가 장애 부재의 증거는 아니다.

### 8.3 기존 Snapshot 활용

현재 순서:

```text
추론 → 상태 판정 → 세션 DB 저장 → Snapshot 전송 성공 확인
→ 이후 처리 → 입력 Kafka offset 커밋
```

Snapshot은 입력 `message_id`를 `snapshot_id`로 재사용하고 가구·측정시각·6종 가전 상태를 제공한다.
따라서 해당 입력이 추론과 세션 DB 저장 단계까지 도달했다는 긍정적 증거로 사용할 수 있다.

추가로 필요한 것:

- Snapshot을 레이크에 보존하고 입력 ID로 대응하기.
- 재처리 동일 ID의 중복 및 다른 결과 충돌 정책. 입력 ID만으로 다른 모델 재추론 결과까지 합치지 않기.
- 분석 모델·파이프라인 버전, 상태 초기화 구간, 입력 범위 식별.
- Snapshot 부재가 분석 실패인지 Snapshot 전달 지연인지 구분하기.
- Snapshot과 세션 변경분의 레이크 전달을 연결하기. Snapshot 존재만으로 세션 전달 완료를 선언하지 않기.

### 8.4 처리 건수 비율로 COMPLETE를 선언하지 않기

`추론 횟수 / observed_slot_count >= 임계 AND GAP 없음`은 완료 조건으로 부족하다.

1. 단순 카운터는 재처리 중복을 셀 수 있고, 묶음 기록은 장애 시 유실될 수 있다.
2. Silver 슬롯과 메시지별 추론 건수는 단위가 다를 수 있다.
3. 추론 성공은 세션 저장·레이크 전달 완료와 다르다.
4. 일일 처리율이 높아도 특정 루틴 시간에 누락이 집중될 수 있다.
5. 워밍업을 분모에서 빼면 실제 분석되지 않은 시간의 영향이 가려질 수 있다.

제안하는 커버리지:

```text
분석 커버리지 = 성공 증거와 연결된 유효 관측 슬롯 수 / 유효 관측 슬롯 수
```

분모는 동일 입력 snapshot·대표 계측기·슬롯 규칙에 맞춘다. 하루 비율과 시간대별 공백을 함께 제공한다.
커버리지는 품질 근거이며 완료 선언이나 전달 확인을 대체하지 않는다.
건수만으로 해당 모델의 전체 윈도우·히스테리시스가 정상 준비되었는지까지 증명하지 못하므로 워밍업·리셋 구간도 추적한다.

### 8.5 단계별 구현과 상태 분리

1. 입력 단위·식별자·모델 버전·완료 기준을 먼저 정의한다.
2. Snapshot과 GAP/RECOVERED 적재로 알려진 분석 성공·장애를 보존한다.
3. 입력과 성공 증거를 연결해 중복 없는 커버리지와 누락 구간을 계산한다.
4. 세션 변경분의 전달 확인을 연결한다.
5. 날짜 마감·지연 도착·수정 revision·재검사 계약을 구현한다.

상태는 서로 다른 개념으로 나눈다:

```text
analysis_status: COMPLETE / INCOMPLETE / ERROR / UNKNOWN
delivery_status: VERIFIED / PENDING / UNKNOWN
quality_flags: INFERENCE_GAP / WARMUP / OPEN_SESSION / ...
```

COMPLETE의 표본·누락 허용 정책은 모델 입력 단위와 업무 요구를 기준으로 확정해야 한다. 관측 VALID 기준 95%를 분석 완료 임계값으로 그대로 복사하지 않는다.
기존 설계 §4.3의 전체 계약을 한 번에 만드는 대신 나눠 구현하되, 증거가 약한 단계를 COMPLETE로 승격하지 않는다.

## 9. Gold baseline 생성

최근 28일의 활성 일별 요약 버전을 고정해 가구·가전별 계산한다.

| 항목 | 계산 |
|---|---|
| `sample_days` | baseline_eligible인 날짜 수 |
| `active_days` | eligible이면서 is_used=true인 날짜 수 |
| 사용일비율 | active_days / sample_days |
| 기대시각 | 사용일별 첫 유효 사용시각의 P90 |
| 중앙 첫 사용 | P50 |
| 선호 시간대 | P10~P90 |
| 요일 패턴 | 같은 요일의 표본·사용일·P90 |

기존 코드 기본값은 최근 28일, 최소 14일, 요일별 최소 4일, 활성화 사용일비율 0.70이다.
백분위는 정렬 후 `ceil(p*N)`번째 값을 선택한다. 일반 보간 또는 근사 백분위로 조용히 교체하지 않는다.
신뢰도는 현재 `min(1, sample_days/14)`이고 14일 미만은 생성하지 않으므로 새로 계산되는 값은 항상 1이다. 개선하려면 별도 정책 변경으로 다룬다.
DB의 `active_days`는 실시간 분석 스키마에서 `normal_days`로 변환된다. 정상 판정을 받은 날짜 수가 아니라 유효 사용일 수다.

새 정책은 분석 품질을 반영하므로 같은 가구라도 가전별 eligible 날짜 수가 달라질 수 있다. 기존 가구 공통 분모와의 차이를 검증한다.

기준 시점:

- 날짜 D의 상태를 평가할 때 D-1까지의 데이터로 만든 프로필을 사용한다.
- D의 데이터를 포함한 프로필은 다음 평가 시점부터 적용한다.
- 과거 평가 재현은 당시 적용 프로필을 사용한다. 최신 데이터로 수정 재평가한 결과는 별도 revision으로 구분한다.

## 10. Gold 시간대별 통계 프로필

일별 요약 외에 모니터링에서 현재 값을 비교할 분포를 만든다.

| 통계 그룹 | 배치 산출값 | 입력 요구사항 |
|---|---|---|
| 루틴 | 사용일비율, 첫 사용 P50/P90, 요일 패턴 | 일별 사용 요약 |
| 무활동 | 같은 시간대의 경과시간 중앙값·MAD·백분위 | 활동 구간·관측/분석 공백 |
| 활동량 | 동일 시각까지 누적 사용 횟수·활동량 분포 | 논리 사용의 발생 시각 |
| 지속시간 | 가전별 완료 논리 사용의 지속시간 분포 | 날짜 경계로 잘리기 전 사용 episode |
| 최근 변화 | 최근 7일과 이전 비교 기간의 변화 | 품질을 통과한 일별 요약 |
| 품질 | 표본 수, 제외 사유, 관측/분석 커버리지 | 관측일·분석 증거 |

무활동은 시간상 연속으로 분석 가능한 구간에서 정의한다. 센서·추론 공백을 무활동 시간에 합치지 않는다.
현재 10시까지의 활동을 과거 하루 전체 활동과 비교하지 않는다. 같은 시각·시간대·요일 조건을 맞춘다.
무활동 현재 경과시간은 과거 같은 시각에서 관측한 경과시간과 비교한다. 완료된 무활동 구간 길이 분포와 섞지 않는다.
가전 사용 지속시간의 `실제 ON 시간`과 `병합 간격을 포함한 경과시간` 중 무엇을 평가하는지 계약에 고정하고 현재 값과 과거 분포를 같은 정의로 계산한다.

프로필 필수 메타데이터:

```text
household_id, profile_version, revision
window_start_date, window_end_date, effective_from
timezone, weekday_group, time_bucket
sample_count, eligible_day_count, quality_status
model_version 또는 명시적 UNKNOWN, rule_version, input_snapshot_id
```

요일별 표본이 부족하면 요일별 → 평일/주말 → 전체 순으로 완화하는 정책을 검토한다. 이는 현행 baseline의 자동 동작이 아니라 새 프로필 정책이다.
28일 창의 같은 요일은 최대 4회이므로 극단적인 백분위까지 정밀하게 추정했다고 표현하지 않는다. 최소 표본과 최소 변동폭을 관리한다.

## 11. 모니터링의 위험 평가 책임

앞선 `household_risk_features_daily` 제안은 다음처럼 세분화한다.

- 배치: 과거 통계, 일별 사실, 최근 기간 변화 제공.
- 모니터링: 현재 지연·현재 무활동·현재 활동 감소를 통계와 비교하고 점수 계산.
- 일일 배치가 생성한 변화값은 근거로 사용할 수 있지만 최종 점수의 주체는 모니터링 하나로 유지한다.

### 11.1 평가 자격

| 상태 | 처리 |
|---|---|
| 충분한 과거 이력 + 현재 관측·분석 정상 | 개인 통계로 평가 |
| 이력 부족 | LEARNING, 정의된 초기 정책 적용 또는 평가 보류 |
| 현재 센서·추론·상태 전달 지연 | 해당 지표 평가 불가 |
| 외출 | 부재 기반 평가 제외, 장시간 켜짐은 별도 검토 |
| 오래된 프로필 | 유효기간에 따라 제한 평가 또는 갱신 필요 |

평가 출력은 분리한다:

```text
risk_score: nullable
risk_level: nullable NORMAL / WARNING / DANGER
assessment_status: VALID / PARTIAL / LEARNING / INSUFFICIENT_DATA
confidence: 별도 값 또는 등급
excluded_indicators, exclusion_reasons
```

평가 불가를 0점·정상으로 표시하지 않는다. 마지막 유효 평가는 평가 시각과 함께 별도로 보관한다.
일부 지표만 평가 가능한 경우 누락 지표를 0으로 넣지 않는다. PARTIAL 전용 집계·알림 정책을 정의하며 전체 정상 판단과 구분한다.

### 11.2 점수식 후보 — 미검증 정책안

아래 식은 첨부에서 논의한 실험 후보다. 사고 확률을 뜻하지 않으며 운영 확정식이 아니다.
`clip(x)`는 0~1 제한이다. 모든 시간 단위는 식 안에서 통일한다.

**루틴 미사용 M**

```text
p = 사용일비율
delay = clip((현재 시각 - 첫 사용 P90) / max(P90-P50, 최소 유예시간))
가전별 점수 = p × delay
M = 평가 가능한 가전별 점수의 최댓값
```

현재 이미 유효하게 사용한 가전의 미사용 점수는 0이다. P90 이전도 0이다. 현재 관측·분석의 연속성이 확인되지 않으면 미사용 확정을 보류한다.

**무활동 I / 활동 감소 A / 장시간 사용 U**

```text
s = max(1.4826 × MAD, 최소 변동폭)
무활동·장시간 사용: z = max(0, (현재 값 - 중앙값) / s)
활동 감소:         z = max(0, (중앙값 - 현재 값) / s)
지표 점수 = clip((z-a)/(b-a)), b > a
```

MAD는 중앙값으로부터의 절대편차의 중앙값이다. 작은 표본이나 MAD=0에서도 분모가 0이 되지 않게 한다.
`a=2`, `b=6` 등은 실험값이다. 장시간 사용은 가전별 점수 중 최댓값을 U로 하는 방안을 검토한다.
현재 세션이 열려 있더라도 최신 상태가 끊겼다면 사용시간을 무한히 늘리지 않는다.

**최종 점수 후보**

```text
B = max(M, I, A)
R = round(100 × min(1, max(B,U) + 0.1 × min(B,U)))
```

부재 관련 상관 지표를 중복 합산하지 않고 강한 신호를 유지하려는 후보식이다. 계수 0.1은 미검증이다.
이 식은 필요한 지표가 평가 가능한 경우를 전제로 한다. PARTIAL에서는 별도 정책이 필요하다.
신뢰도를 점수에 단순 곱해 데이터 부족을 낮은 위험으로 바꾸지 않는다.

### 11.3 등급·알림 정책

현재 모니터링의 기본값은 주의 70, 위험 90이다. 새 점수식에서도 적합하다는 검증은 아직 없다.

정책 버전에는 다음을 포함한다:

- 주의·위험 임계값, 상승 유지시간, 복귀 임계값·유지시간
- 지표별 표본 하한, 유예시간, 최소 변동폭
- 외출·수면·모니터링 중지 처리
- 프로필 유효기간, 현재 상태 freshness, 알림 재발송 간격
- 부분 평가·학습 중·입력 부족 시 처리

개인별 통계와 공통 임계값으로 시작한 뒤 실제 확인 결과로 조정한다. 정상 이력의 P95/P99만으로 위험 임계값을 자동 확정하지 않는다.
상태 변화와 타이머 평가를 함께 사용하고, 동일 판단·동일 사건의 반복 알림을 방지한다.

### 11.4 기존 알림 경로와 판단 주체 분리

판단 주체 전환은 분석 서비스의 알림을 모두 모니터링으로 옮기는 것이 아니다. 이벤트 유형별로 소유자를 나눈다.

| 판단 | 소유자 | 근거 |
|---|---|---|
| 장시간 사용 `PROLONGED_APPLIANCE_USE` | 분석 서비스, 즉시 알림 유지 | 사용 세션 시작 시각과 가전별 허용 시간만으로 판정한다. 프로필·학습 기간이 필요 없고, 세션 ID 기반 결정적 `event_id`로 세션당 한 건이 보장된다. 모니터링은 스냅샷 상태만 갖고 있어 세션 시작 시각을 분석 서비스만큼 정확히 알지 못한다. |
| 루틴 미사용 `ROUTINE_MISSED` | 모니터링 M 지표로 이전 | 과거 프로필과 당일 실시간 품질을 함께 봐야 한다. 기존 이벤트는 shadow 비교 후 근거로 격하한다. |
| 무활동 `PROLONGED_INACTIVITY` | 전환기에는 분석 서비스 즉시 알림, 이후 모니터링 I 지표 | 고정 시간 임계 판정은 즉시 알림으로 유지할 수 있다. 개인별 시간대 분포 비교가 준비되면 지표별로 전환한다. |
| 루틴 변화 `ROUTINE_CHANGED` 등 일일 결과 | 저장만, 보고서 근거 | 실시간 알림 대상이 아니다. |

> **2026-09-27 변경.** 무활동은 분석 서비스가 계속 소유한다. 모니터링은 루틴 기준선을 점수에 쓰지 않고, M·I 지표를 전환하지 않고 제거했다(`monitoring-score-v2-A`). 루틴 미사용은 어느 쪽도 판단에 쓰지 않는다. `ROUTINE_MISSED`는 `SHADOW`로 두어 저장·화면 표시만 하고 등급·알림을 만들지 않는다. 모니터링 자체 평가는 활동 감소 A만 계산하고, 그 점수는 등급·알림 없는 참고값이다. 화면 등급은 이벤트 슬롯에서만 온다. 아래 "ROUTINE_MISSED 전환 절차"는 폐기한다. 루틴 미사용을 다시 알림에 쓰려면, 분석 서비스의 `has_usable_observation`이 당일 관측 한 건만 보고 커버리지 비율은 보지 않는 문제부터 해결해야 한다.

**이벤트 유형별 라우팅 정책**

모니터링의 이벤트 소비는 단일 흐름 대신 유형별 정책으로 나눈다. 정책은 설정으로 바꾸고 버전을 기록한다.

```text
IMMEDIATE:<등급>  즉시 해당 등급으로 알림. 계약에 score가 없으므로 등급을 유형별 고정값으로 정한다.
SHADOW            저장·화면 표시만 하고 등급 반영·알림을 하지 않는다. 모니터링 자체 평가와 비교하는 기간에 쓴다.
EVIDENCE          저장만 한다. 알 수 없는 유형의 기본값으로 두어 새 유형이 와도 소비자가 멈추지 않게 한다.
```

정책 항목에는 등급, 외출 중 억제 여부, 응답 요구 여부·기한을 포함한다. 장시간 사용은 부재 중일수록 위험하므로 외출 중에도 알림을 낸다. 현재 코드의 “외출 중 발생이면 알림 생략”을 모든 유형에 일괄 적용하지 않는다.

현행 코드는 수신 `score`를 필수로 검사하지만 분석 서비스의 이벤트 계약에는 `score`가 없다. 실제 이벤트가 오면 소비자가 정지하므로 라우팅 도입 전에 이 검사를 먼저 제거한다.

**즉시 알림 경로와 자체 평가의 충돌 방지**

- 장시간 사용 판단을 분석 서비스가 소유하는 동안 모니터링 점수식에서 U를 뺀다. 11.2의 `max(B,U) + 0.1 × min(B,U)` 결합은 U 소유권을 넘겨올 때 다시 적용한다. 수신한 `PROLONGED_APPLIANCE_USE` 이벤트는 U의 호환 입력으로 평가 이력에 기록해 보고서 근거를 잇는다.
- 이벤트 기반 등급과 자체 평가 등급은 별도 슬롯에 보관하고, 화면·스트림에 내보내는 유효 등급은 둘 중 높은 값으로 한다. 타이머 평가가 낮은 점수를 내더라도 이벤트 등급을 덮어쓰지 않는다.
- 이벤트 등급 해제 조건은 해당 가전의 ON→OFF 전환 확인, 담당자의 조치 완료 처리, 안전장치로서의 최대 유지시간 경과 세 가지다. reason의 `appliance_type`으로 전환을 대응시킨다.
- 즉시 알림의 중복 방지는 결정적 `event_id`와 이벤트당 알림 1건 규칙으로 충분하다. 분석 서비스의 cooldown도 그대로 둔다.
- 알림 문구는 유형별 템플릿과 reason 값으로 만든다. 현재의 유형 무관 고정 문구는 쓰지 않는다.

**ROUTINE_MISSED 전환 절차**

1. `SHADOW`로 두고 모니터링 M 지표를 병행 계산한다. 같은 날·같은 가전에서 기존 이벤트 발생 시각과 M이 임계를 넘은 시각의 차이, 그리고 신규 경로의 PARTIAL·INSUFFICIENT_DATA 비율을 비교한다.
2. 첨부의 “사용일비율이 임계 아래로 내려가면 ROUTINE_MISSED 발송” 설명은 현행 코드와 다르다. 현재는 baseline 강도가 낮으면 판단을 건너뛴다. 실제 오판 가능성은 당일 추론 누락으로 사용 이력이 없는데 기존 baseline 강도는 충분한 경우다. 이 경우가 신규 경로에서 평가 제외로 잡히는지 확인한다.
3. 비교가 끝나면 `EVIDENCE`로 내리고 M 지표가 알림을 소유한다. 되돌리기는 라우팅 정책을 `IMMEDIATE`로 바꾸는 것으로 끝나야 한다.

## 12. 배치 결과 전달과 평가 이력

프로필 전달 순서:

```text
Gold 검증 → 파일·manifest 확정 → ACTIVE 버전 + 전달 outbox 기록
→ Kafka 전달 → 모니터링 수신·검증 → 최신 프로필 반영
```

파일과 Kafka를 단일 트랜잭션으로 취급하지 않는다. DB 활성화와 전달 작업 등록은 한 트랜잭션으로 처리하고 발행을 재시도한다.
중복 수신, 늦은 구버전 도착, 과거 backfill이 최신 프로필을 덮어쓰는 문제를 방지한다.
프로필은 버전·적용 시각으로 선택하고 평가 한 번 안에서는 입력 프로필을 고정한다.

평가 이력 필드:

```text
assessment_id, household_id, assessed_at, data_as_of
risk_score, risk_level, assessment_status, confidence
M, I, A, U, 실제 관측값, 비교 통계값
profile_version, policy_version, score_version
현재 입력 식별자·품질 상태
등급 변경·제외·알림 사유, revision
```

평가 이력도 레이크에 적재한다. 과거 정책 재평가 결과와 당시 실제 발송 이력을 구분한다.

## 13. 보고서 생성

가구별 보고서에는 관측·분석 품질, 가전 사용 현황, 평소 대비 변화, 실제 평가된 점수·등급·근거를 담는다.
운영 보고서에는 입력·정제·중복·오류 건수, 파일 병합 효과, 지연·실패·재시도, UNKNOWN 비율을 담는다.

보고서 규칙:

- 배치가 최종 위험 점수를 새로 계산하지 않고 실제 모니터링 평가 이력을 사용한다.
- 평가가 없거나 데이터가 부족하면 그 사실을 표시한다. 정상으로 채우지 않는다.
- 대상 기간, 입력 snapshot, 프로필·정책·점수식 버전, 생성 시각을 보존한다.
- 지연 데이터나 정정으로 수정되면 이전 보고서를 덮어 없애지 않고 revision을 남긴다.
- 일일/주간 형식과 HTML/PDF 여부는 후속 구현에서 확정한다.

## 14. 자동화·멱등성·재처리

단일 노드에서는 기존 배치 제어를 확장해 순서와 성공 조건을 관리한다. 새 플랫폼 도입 자체가 선행 조건은 아니다.

일일 실행 순서:

1. 입력 준비와 세션 초기 적재 상태 확인.
2. 전력 Silver 생성·검증·활성화.
3. 세션 최신 상태와 분석 증거 snapshot 고정.
4. Silver 논리 사용·Gold 일별 요약 생성.
5. 기존 프로필로 대상 날짜 변화를 평가할 근거 확정.
6. 다음 평가에 사용할 baseline·통계 프로필 생성·전달.
7. 실제 평가 이력을 적재하고 보고서 생성.
8. 실행 이력과 완료 상태 기록.

모니터링의 실시간 평가는 이 배치와 독립적으로 계속 실행한다. 보고서만 필요한 입력·평가 이력의 준비를 기다린다.

공통 실행 계약:

- 대상 날짜·입력 목록·해시·규칙·설정 버전을 고정한다.
- 실패한 단계에서 재시도하고 같은 입력의 성공 결과는 재사용한다.
- 불변 run 경로에 쓰고 검증한 manifest와 ACTIVE 포인터로 공개한다.
- 오래된 실패 실행의 복구가 새 활성 결과를 되돌리지 않게 한다.
- 서버 중단 중 누락된 날짜를 목록으로 찾아 복구한다. 최신 하루만 처리하고 끝내지 않는다.
- `batch_run`의 날짜별 성공 여부만으로 수정 재처리를 표현하지 않는다. 레이크 버전 이력을 사용한다.

수정 영향:

- 세션 변경은 이전·새 상태가 겹치는 날짜의 합집합을 재처리한다.
- 삭제는 이전 상태에서 영향 범위를 찾는다. 임의의 짧은 lookback으로 한정하지 않는다.
- 날짜 D의 요약 수정은 D~D+27 기준일의 28일 baseline에 영향을 줄 수 있다.
- 관측 Silver와 분석 증거가 변경되면 기존 의존 결과를 재검사한다.
- 과거 재처리는 현재 프로필을 되돌리거나 과거 알림을 자동 재발송하지 않는다.
- DB 보관 만료 삭제와 사실 정정 삭제는 구별해야 한다. 현재 세션 DELETE만으로는 이 목적을 구별할 수 없다.

## 15. 단일 노드와 분산 확장

Spark는 연산 엔진이고 HDFS는 저장 계층이다. 단일 서버의 여러 컨테이너는 물리적 장애 분리를 제공하지 않는다.

초기에는 같은 업무 로직을 Spark local 모드로 검증하고, 실행 주소와 자원 설정을 외부화한다. 모든 worker가 접근할 HDFS 경로와 동일 이미지·라이브러리 버전을 사용한다.

주요 고려사항:

- Kafka·DB·분석기와 CPU·메모리·디스크를 공유하므로 Spark 자원을 제한한다.
- JVM 힙 외에 Python·직접 메모리·OS 여유 공간을 확보한다.
- 원본·결과 외에 shuffle·spill·임시 결과 공간도 예산에 포함한다.
- 원천 전체 collect/pandas 변환을 피하고 Spark 분산 연산을 유지한다.
- 날짜·가구별 분할 수와 데이터 쏠림을 측정한다.
- DB JDBC 연결 수를 제한한다. 원천 세션 반복 조회 대신 레이크를 사용한다.
- 작은 데이터에서는 Spark 실행 비용이 더 클 수 있으므로 기존 처리와 비교한다.

확장 순서:

| 단계 | 구성 | 검증 |
|---|---|---|
| 1 | 단일 노드 전체 자동화 | 정확성·재처리·종단 소요시간 |
| 2 | 다른 서버에 Spark worker 추가 | 연산 확장 효과 |
| 3 | HDFS DataNode 추가 | 저장 분산·I/O·복제 영향 |
| 4 | worker/DataNode 중단 | 복구·중복·데이터 접근 |

DataNode 추가만으로 기존 블록이 균등 재배치되었다고 가정하지 않는다. 실제 블록 배치·복제 상태를 확인한다.
단일 NameNode가 남으면 그 노드는 여전히 단일 장애 지점이다. worker 복구와 저장 가용성을 구분해 평가한다.

비교는 입력 snapshot·규칙·결과 정의를 고정한다. 1→2→N 노드의 전체 자원을 늘리는 실험과 전체 자원을 같게 유지하는 실험을 구분하고 기록한다.
업무 결과 해시는 run ID·시각·파일명 등 실행 메타데이터를 제외해 비교한다.

## 16. 검증 계획과 운영 전환 조건

| 영역 | 필수 사례 |
|---|---|
| 관측 | 정상·0건·95% 경계·중복·버스트·부분 관측·기기 교체 |
| 세션 | SNAPSHOT 중복·역순 버전·DELETE·동일 버전 충돌·날짜 이동 |
| 사용 판정 | 10초 경계·병합 간격 경계·자정·미종료·시간 중복 |
| 분석 증거 | 재시작 워밍업·GAP 복구·추론 실패·Snapshot 지연·세션 전달 지연 |
| 품질 | 정상 미사용 false와 분석 불가 null 구분, UNKNOWN 분모 제외 |
| 프로필 | 평가일 데이터 미포함·요일 표본 부족·MAD=0·같은 시각 비교 |
| 모니터링 | 외출·상태 지연·타이머 평가·부분 평가·중복 알림·복귀 기준 |
| 복구 | manifest 후 DB 실패·오래된 실행 복구·동시 실행·누락 날짜 |
| 분산 | worker 수 변경에도 같은 결과, 장애 중 재실행 |

DB 병행 비교는 두 종류로 나눈다.

- 정상·완료·비중복·당일 세션: 첫 사용·횟수·시간 등 정확한 일치를 요구한다.
- 정책 차이: Silver 슬롯 수집률, 미종료 제외, 부분 관측 제외, 실제 날짜 겹침 등은 의도된 차이로 분류하고 영향 건수를 확인한다.

운영 전환 조건:

1. 입력·출력 계약과 분석 증거 생산·전달이 연결됨.
2. 동일 snapshot 재처리와 노드 수 변경에서 결과가 재현됨.
3. 품질 부족이 정상 미사용이나 낮은 위험으로 바뀌지 않음.
4. 과거 수정·실패 복구·버전 전환이 검증됨.
5. 점수식·임계값을 시간 순서의 검증 데이터와 확인 결과로 평가함.
6. 기존 알림과 신규 평가의 소유권·중복 방지·되돌리기 절차가 정해짐.

관측 지표: 단계별 시간, 처리량, 최대 메모리, shuffle/spill, 디스크·네트워크 I/O, Kafka lag,
DB 지연, UNKNOWN 사유, profile freshness, 알림 수·확인 결과·탐지 지연.

## 17. 구현 순서와 미확정 항목

### 우선순위

1. **분석 증거 계약부터 확정:** 입력 식별·Snapshot 활용·완료 기준·전달 장벽.
2. **병행 개발:** 세션 복원·논리 사용·Gold 일별 요약과 분석 증거 적재.
3. **품질·복구 연결:** 버전 고정, dirty-date, shadow 비교, 실패 복구.
4. **Gold 통계 확장:** baseline, 시간대 활동·무활동, 지속시간, 최근 변화.
5. **모니터링 shadow 평가:** 프로필 수신, 현재 품질, 정책, 점수·등급·평가 이력.
6. **보고서 자동화:** 실제 평가 이력과 확정 통계 연결.
7. **운영 전환 및 분산 실험:** 알림 소유권 전환 후 노드 수·장애 비교.

### 확정이 필요한 사항

- 분석 단위와 완료 조건, 허용 공백, 상태 초기화·워밍업 처리
- Snapshot 계약 확장과 세션 전달 장벽의 구체적 구현
- 시간대 bucket 크기, 시간대별 최소 표본, 프로필 fallback 규칙
- 미종료·중복 세션의 정정과 자정 episode 복원 방법
- 지속시간의 실제 ON 시간/경과시간 정의
- 부분 평가의 점수·등급·알림 정책
- 점수식 계수·주의/위험 임계·해제 조건
- 프로필·레이크·평가 이력 보관 기간과 DB 만료 삭제 의미
- 보고서 형식과 배포·조회 방식
- 단일 노드 자원 예산과 분산 테스트 데이터 규모
