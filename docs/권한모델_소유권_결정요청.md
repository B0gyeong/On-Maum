# 권한 모델 정리 — 보호자(GUARDIAN) 제거와 남은 제약

작성: 채지현 (2026-09-21) · 대상: 백엔드·AI·프론트 전원
**상태: 1차 조치 완료 · 2차 항목은 결정 필요**

## 요약

`device_db`와 `monitoring_db`가 "누가 어느 가구를 볼 수 있는가"를 각자 다른 모델로 판정하고 있었다.
그 결과 **초대 코드로 정식 합류한 보호자가 모니터링 데이터에서 전부 403**을 받았다.

절반만 구현된 역할을 남겨두면 사용자에게는 고장으로 보이므로 **보호자(GUARDIAN)를 제거했다**(V8).
남은 제약은 **담당자를 대상자 한 명당 한 명만 배정할 수 있다**는 것이며, 이건 결정이 필요하다.

## 용어 (담당자 ≠ 보호자)

| 용어 | 코드 값 | 누구 | 상태 |
| --- | --- | --- | --- |
| **대상자** | `SELF` | 모니터링 받는 본인 | 사용 중 |
| **담당자** | `STAFF` | 복지사 등 기관 직원 | 사용 중 |
| ~~보호자~~ | ~~`GUARDIAN`~~ | ~~가족·지인~~ | **제거됨 (V8)** |

가입 시 `organization` 입력 여부로 갈린다. 값이 있으면 담당자로 보고 아웃박스를 거쳐
`monitoring_db.managers`에 올린다. 없으면 `user_profiles`에만 남는다.

> 같은 사람을 층마다 다르게 부른다: 프론트 "복지담당자" / monitoring `managers` /
> device_db `relation = STAFF`. 전부 동일 인물이다.

## 1부 — 왜 제거했나 (조치 완료)

### 재현했던 문제

정상 경로로 보호자를 H001에 합류시킨 뒤 조회하면 전부 막혔다.

```
보호자 가입 → 201
대상자 본인이 GUARDIAN 초대 코드 발급 → 201
보호자가 코드 수락 → 201, relation=GUARDIAN
GET /api/auth/me → households: [{ houseId: "H001", relation: "GUARDIAN" }]   ← 여기까진 정상
```

| 엔드포인트 | 보호자 | 배정 담당자 |
| --- | --- | --- |
| `GET /api/monitoring/subjects/1/events` | **403** | 200 |
| `GET /api/monitoring/subjects/1/power-usage` | **403** | 200 |

응답: `"배정된 담당자만 대상자 정보를 조회할 수 있습니다."`

### 원인

`monitoring`에는 **GUARDIAN 개념 자체가 없고** `household_members`를 읽지도 않는다.
판정은 `SubjectAccessGuard`가 `subjects.manager_id` 하나로만 한다.

```java
if (authSub.equals(subject.getAuthSub())) return subject;   // 대상자 본인
boolean assignedManager = managers.findByAuthSub(authSub)
        .map(m -> Objects.equals(m.getId(), subject.getManagerId()))
        .orElse(false);                                      // 배정된 담당자 한 명
if (!assignedManager) throw ... FORBIDDEN;
```

보호자는 `managers`에 없으므로 `findByAuthSub`가 비고 곧바로 403이다.

### 조치 (V8__remove_guardian_relation.sql)

- 미사용 GUARDIAN 초대 삭제, 사용 이력 있는 초대는 `STAFF`로 승계
- GUARDIAN 멤버십 삭제 — 어차피 어떤 조회도 통과하지 못했으므로 잃는 접근 권한이 없다.
  기관 소속이 아닌 사람에게 담당자 권한을 줄 수는 없으므로 STAFF 승격은 하지 않았다
- `household_members` · `household_invites` 체크 제약에서 `GUARDIAN` 제외
- `relation` 컬럼의 기본값(`GUARDIAN`) 제거 — **SELF와 STAFF 사이에는 합리적 기본값이 없다.**
  조용히 한쪽으로 정해지면 권한이 잘못 부여되므로 엔티티에서도 명시를 요구하도록 바꿨다

적용 확인: `household_members` STAFF 2 / SELF 10, GUARDIAN 0. 제약 위반 삽입 시도 → 거부됨.
단위 테스트 57건 통과.

## 2부 — 남은 제약 (결정 필요)

보호자를 걷어내도 **담당자 쪽 제약은 그대로 남는다.**

`subjects.manager_id`는 컬럼 하나라 **대상자 한 명에 담당자 한 명**만 배정할 수 있다.
구조적으로 두 명을 담을 수 없다.

### 언제 문제가 되나

- 담당 복지사가 휴가·퇴사할 때 대체 인력이 볼 수 없다
- 야간·주말 당직 담당자에게 넘길 수 없다
- 한 어르신을 두 기관(주민센터 + 복지관)이 함께 보는 경우를 표현할 수 없다

지금 시연 시나리오(담당자 1명 : 대상자 N명)는 정상 동작하므로 **급하지는 않다.**

### 선택지

**A. 그대로 둔다.** 1:1 배정이 기획 의도라면 아무것도 할 필요 없다. 다만
`household_members`의 N:M 모델과 뜻이 겹치므로 **device_db 쪽을 담당자 배정의 원본으로
쓰지 않는다는 점을 계약 문서에 명시**해야 한다. 지금은 양쪽 다 권한의 원본처럼 보인다.

**B. monitoring에 배정 테이블을 만든다.** `subjects.manager_id`를
`subject_assignments(subject_id, manager_auth_sub)`로 바꿔 N:M을 지원한다.
monitoring 안에서 끝나므로 서비스 간 계약 변경이 없다.

**C. device_db를 권한의 원본으로 삼고 이벤트로 잇는다.** 멤버십 변경 시
담당자 가입과 같은 아웃박스 방식으로 발행(`device.household-membership-changed.v1`)하고,
monitoring이 자기 읽기 모델을 채운다. 판정은 monitoring이 로컬에서 하므로
device-service가 죽어도 조회는 계속된다.

보호자가 없는 지금은 **B로 충분하다.** C는 device_db의 멤버십을 권한의 원본으로 승격하는
큰 변경인데, 지금은 담당자만 있으므로 그만한 값을 하지 못한다.
**나중에 보호자를 되살린다면 그때 C가 답이 된다.**

## 합의 절차 제안

**1단계 — 기획 확인 (이게 먼저다)**
안건 둘을 기획에 묻는다. 기술 논의보다 앞선다.

- **"보호자(가족·지인)가 대상자 데이터를 봐야 하는가?"** — 기획서에는 있었으나 구현이
  절반이라 일단 제거했다. 필요하다면 되살려야 하고, 그때는 두 서비스 권한 모델을 함께 설계한다
- **"대상자 한 명을 담당자 여러 명이 봐야 하는가?"** — 아니오면 2부는 A로 끝난다

**2단계 — monitoring 담당자 확인**
`manager_id` 1:N이 **의도한 제약인지, 아직 확장 안 한 것인지** 확인이 필요하다.
의도된 설계라면 그 이유가 있을 테고 논의의 전제가 바뀐다.

**3단계 — 결정 후 즉시 계약 문서화**
선택한 안을 `docs/파트간_계약_초안.md`에 추가한다. 최소한 이 두 가지:
**각 서비스가 소유하는 테이블**과 **판정 책임의 경계**. 지금은 이게 없어서
양쪽이 각자 권한 모델을 키웠다.

## 지금 알아둘 것

- **시연 시나리오는 영향 없다.** 담당자 1명이 대상자를 보는 흐름은 정상 동작한다
- **프론트에 보호자 초대 UI가 있다면 제거해야 한다.** 이제 서버가 `GUARDIAN`을 거부한다
  (`400 VALIDATION_ERROR`). 초대 코드 기능 자체는 살아 있고 `STAFF` 초대에 쓴다
- 중간평가에서 질문받으면 "보호자는 권한 모델 통합 전까지 제거했다"가 정확한 답이다
