# 이벤트 reason 조합 위험 점수 집계 설계 — 대상자 간 비교용

작성 2026-09-27. 수정 2026-09-28.

이 문서는 현재 구현을 설명하는 0장과, 아직 구현하지 않은 대상자 비교 점수 설계를 구분한다. 비교 점수는 기존 등급·알림 정책을 대체하지 않는다. Incident는 현재 없으며 이 설계에서도 도입하지 않는다.

## 0. 서비스 역할과 기준선 전달

### 0.1 책임 구분

배치는 **평소 생활의 기준**, 실시간 분석은 **현재 발생한 상황**, 모니터링은 **상태 표시·평가·알림 정책**을 맡는다. 현재 배치는 일일 집계와 Gold 프로필 생성의 두 경로로 나뉜다.

| 서비스 | 입력 | 책임 | 출력 |
|---|---|---|---|
| 실시간 분석 | 전력 데이터, 분석용 루틴 기준선, 분석 정책 | 가전 상태·사용 구간 추정, 이상 이벤트 감지, 관측·사용 이력 저장 | `analysis.snapshot.v1`, `analysis.event.v1`, 분석 DB의 사용·관측 이력 |
| 일일 집계 배치 `aggregation_service` | 분석 DB의 사용·관측 이력 | 일일 활동 지수 계산, 루틴 기준선 갱신 | `analysis.activity.v1`, 분석 DB의 `routine_baseline` |
| Gold 배치 `gold_profile_service` | 데이터 레이크의 과거 사용·관측 데이터 | 최근 28일 루틴 및 생활 통계 계산 | 버전이 있는 Gold 데이터와 `gold.household-profile.v1` |
| 모니터링 | 이벤트·스냅샷, Gold 프로필, 외출·연결·응답 상태 | 현재 상태 관리, 활동 감소 참고 평가, 이벤트 등급 반영, 알림 및 응답 관리 | 대시보드, 평가 이력, Web Push |

실시간 분석이 쌓은 오늘의 이력은 다음 배치의 입력이 된다. 기준선은 배치가 과거를 요약한 값이고, 이벤트는 분석 서비스가 현재 상황을 판단한 결과다. 배치가 최종 위험 등급이나 알림을 결정하지 않는다.

### 0.2 경로 A: 실시간 분석용 루틴 기준선 — DB로 전달

```text
실시간 분석의 관측·가전 사용 이력
  → 분석 DB 저장
  → 일일 집계 배치가 과거 유효 관측일 집계
  → 분석 DB의 routine_baseline 갱신
  → 실시간 분석이 주기적으로 DB를 다시 읽고 캐시 교체
  → 이후 루틴 미사용 판단에 사용
```

예를 들어 유효 관측 20일 중 전기포트를 사용한 날이 18일이면 사용 확률은 0.9다. 첫 유효 사용 시각의 중앙값은 대표 시각이고, 90백분위수는 `expected_until`이다. 실시간 분석은 이 예상 시각과 오늘의 사용 여부를 비교하며, 실제 감지에는 외출·관측 상태 등 분석 규칙도 적용한다.

이 경로는 Kafka로 Gold 프로필을 받아 분석 기준선을 바꾸는 구조가 아니다. `aggregation_service`의 기준선 갱신기와 실시간 분석의 `SqlAlchemyBaselineRepository`가 분석 DB를 통해 연결된다. 장시간 무활동의 기준시간과 가전별 허용시간은 루틴 첫 사용 시각 통계와 별개의 분석 정책이다.

### 0.3 경로 B: 모니터링용 Gold 프로필 — Kafka로 전달

```text
데이터 레이크의 사용·관측 이력
  → Silver: 일별 사용량·관측 품질·사용 구간 정리
  → Gold: 최근 28일 루틴·생활 통계 계산
  → 발행 대기 내역(outbox) 저장
  → 발행기가 gold.household-profile.v1 전송·재시도
  → 모니터링 수신·검증·버전 저장
  → 현재 적용 가능한 프로필을 ACTIVE로 선택
```

Gold 프로필은 실시간 분석을 경유하지 않고 모니터링으로 전달된다. 현재 Gold에는 outbox와 발행·재시도 경로가 구현되어 있다. 배치 성공만으로 모니터링 반영까지 성공했다고 단정하지 않으며, 발행 상태와 수신 프로필 상태를 따로 확인한다.

| 프로필 구성 | 의미 | 현재 모니터링 용도 |
|---|---|---|
| `routine_baselines` | 가전별 사용 확률, 첫 사용 시각, 예상 마감 시각 등 | 저장·프로필 화면 표시. 현재 A 계산에는 사용하지 않음 |
| `statistics` | 시간대별 누적 유효 사용 시작 횟수 등의 중앙값·변동폭 | 현재 관측값과 비교하여 활동 감소 A 계산 |

모니터링의 반영 규칙은 다음과 같다.

- 이미 받은 버전은 중복 반영하지 않는다.
- 품질이 부적합한 프로필은 운영 기준으로 채택하지 않는다.
- `SHADOW`는 비교용으로 저장하고 운영 기준을 바꾸지 않는다.
- 현재보다 오래된 날짜·revision은 이력으로 남긴다.
- 적용 시각이 미래인 후보는 `PENDING`으로 저장한다.
- 적용 가능한 최신 정상 프로필은 `ACTIVE`로 선택한다.
- 평가 시점에는 `effective_from`과 `as_of_date`를 확인한다. 평가 당일 이후 데이터로 만든 기준은 사용하지 않는다. 오래된 프로필은 평가 가능 여부에 반영한다.

예를 들어 과거 정오까지 유효 사용 시작 횟수의 중앙값이 6회이고 오늘 정오까지 2회라면, 모니터링은 관측 품질을 확인한 뒤 과거 변동폭까지 고려해 A를 계산한다. 현재 평가는 최근 30분 경계를 맞춰 비교하므로 12:10에 12:30의 기준을 사용하지 않는다.

### 0.4 일일 activity_index와 현재 A는 서로 다르다

| 구분 | 일일 `activity_index` | 현재 모니터링의 활동 감소 A |
|---|---|---|
| 계산 주체 | 일일 집계 배치 | 모니터링 |
| 시간 범위 | 전날 하루 | 현재 평가 기준 시각까지 |
| 비교 기준 | 고정 목표량 | 개인의 Gold 시간대별 과거 통계 |
| 계산 | 횟수 점수 50% + 다양성 점수 30% + 시간 점수 20% | 누적 유효 사용 시작 횟수의 감소와 과거 변동폭 비교 |
| 의미 | 고정 목표에 대한 하루 활동량 | 개인의 평소 대비 활동 감소 참고 점수 |
| 현재 연결 | `analysis.activity.v1` 발행. 모니터링의 수신·위험 변환 경로는 없음 | 현재 참고 평가에 구현됨. 등급·최초 알림은 만들지 않음 |

`activity_index`의 각 점수는 `round(min(값 / 목표, 1) × 100)`이다. 횟수 목표는 6회, 다양성 목표는 3종류, 시간 목표는 3,600초다. 점수용 횟수는 가전 종류별 최대 3회이며, 시간에도 가전별 상한이 있다. 짧은 사용 구간을 병합하고 실제 작동시간 합계가 10초 이상인 사용을 인정한다. 기본 한국 시간 00:10에 전날 지수를 발행한다.

관측 샘플 충족률이 기본 95% 미만이면 지수는 `null/INSUFFICIENT_DATA`다. 관측이 충분하지만 사용이 없으면 `0/VALID`다. 지수 90은 평소의 90%나 안전 확률 90%가 아니다.

이 문서의 결합식에 쓰는 **A는 현재 모니터링의 참고 점수를 100으로 나눈 값**이다. 일일 `activity_index`나 `100 - activity_index`로 바꾸지 않는다. A가 계산 불가하면 이전 점수를 새 평가값처럼 넣지 않고 제외 사유와 마지막 유효 평가 시각을 남긴다.

### 0.5 일일 활동 감소 점수는 별도 후속 설계

일일 지수를 위험 참고값으로 활용하려면 수신·저장 경로와 개인별 비교 기준을 추가해야 한다. 후보식은 다음과 같으며 현재 구현이 아니다.

```text
B_day = 평가일 이전 최근 28일 VALID 일일 지수의 중앙값
X_day = 수신한 평가일의 VALID 지수
D_day = max(0, (B_day - X_day) / B_day)
A_day = 40 × clip((D_day - 0.20) / 0.60)
```

평가일 자신의 값은 기준에 넣지 않는다. 기준이 0이거나 유효 표본이 부족하면 계산 불가로 처리한다. 20%·60%·최대 40점은 검증 전 정책 후보다. 필요하면 평일·주말을 분리한다. `A_day`는 평가 날짜가 붙은 전날 활동 감소값으로 담당자 확인 및 보고서에 활용하며, 현재 이벤트 점수에 바로 합산하거나 즉시 알림을 만들지 않는다. 같은 날짜 메시지는 누적 가산하지 않고 중복 처리 또는 버전 갱신한다.

### 0.6 현재 구현과 이번 변경 범위

- 현재: 분석 이벤트 유형이 등급을 정한다. 무활동은 주의, 장시간 사용은 위험, 루틴 미사용은 SHADOW다. 현재 A는 참고값이다.
- 이번 설계: 이벤트 reason과 현재 A로 **비교 점수**를 추가한다. 등급에서 점수 구간을 정하며, 점수에서 등급을 역으로 결정하지 않는다.
- 여러 활성 이벤트를 보존하는 저장 구조는 새로 필요하다. 기존 이벤트·평가·대상자·알림을 활용하며 Incident는 만들지 않는다.
- 등급을 점수 임계값으로 결정하는 방식, 루틴 미사용을 알림 판단에 포함하는 방식, 일일 활동 감소값을 실시간 점수에 합치는 방식은 이번 범위가 아니다.
- 현재 두 배치의 루틴 기준선은 전달 대상과 저장 경로가 다르다. 후속 통합 시 생성 주체를 하나로 정하거나 계산 규칙·품질 조건·버전을 맞춘다. Gold가 분석용 DB 기준선을 이미 갱신한다고 가정하지 않는다.

## 1. 왜 필요한가

지금 화면 점수는 대상자끼리 비교가 안 된다.

- 이벤트 등급은 유형별 고정 점수(주의 70, 위험 90)로 저장된다. 주의 대상자는 전부 70점, 위험 대상자는 전부 90점이라 같은 등급 안에서 순서가 없다.
- 대상자당 이벤트 슬롯이 하나다(`subjects.event_risk_*`). 무활동과 장시간 사용이 동시에 걸리면 나중 것이 앞 것을 덮어쓴다. 두 가지가 겹친 사람과 하나만 걸린 사람이 같은 점수다.
- 같은 무활동이라도 방금 2시간을 넘긴 사람과 5시간째인 사람이 같은 70점이다.

목표는 **담당자 목록을 위험한 순서로 정렬할 수 있는 점수** 하나다. 사고 확률이 아니다. 알림을 내는 기준도 아니다.

## 2. 지키는 것

- **판단 소유권은 그대로.** 무활동·장시간 사용은 분석 서비스가 판단한다. 모니터링은 이미 내려진 판단의 `reason`을 읽어 **얼마나 심한지**를 점수로 옮길 뿐, 판단을 다시 하지 않는다.
- **등급과 알림은 바뀌지 않는다.** 등급은 지금처럼 이벤트 라우팅(`IMMEDIATE:WARNING/DANGER`)이 정하고, 알림은 지금처럼 이벤트 도착과 재발송 간격으로 나간다. 이 점수는 그 어느 것도 트리거하지 않는다.
- **분석 서비스 계약은 바꾸지 않는다.** 지금 오는 `reason` 필드만 쓴다.
- **루틴 미사용은 판단에 쓰지 않는다**(2026-09-27 결정). 기본 가중치 0으로 두고 설정으로만 켤 수 있게 한다.
- **모르는 것을 0점으로 만들지 않는다.** 계산할 수 없는 구성요소는 빼고, 뺐다는 사실을 근거에 남긴다.

## 3. 입력: 이벤트별 reason

| 이벤트 | reason 필드 (분석 서비스가 지금 보내는 것) | 점수에 쓰는 값 |
|---|---|---|
| `PROLONGED_INACTIVITY` | `inactivity_started_at`, `threshold_hours`, `sleep_window{start,end}`, `last_activity_at`, `last_returned_at` | 임계를 넘긴 뒤 **깨어 있는 시간 기준** 초과분 |
| `PROLONGED_APPLIANCE_USE` | `appliance_type`, `started_at`, `allowed_duration_minutes` | 허용 시간 대비 초과 비율 |
| `ROUTINE_MISSED` | `appliance_type`, `expected_until`, `normal_days`, `window_days` | 사용일 비율과 예상 시각 이후 지연 (기본 가중치 0) |
| `ROUTINE_CHANGED` | `shift_minutes`, 방향 등 (일 배치) | 쓰지 않는다. `EVIDENCE`로 저장만 |

모니터링이 이미 아는 맥락도 입력이다: 외출 여부, 기기 접속 상태, 대상자 응답(예/아니오/무응답), 담당자 조치, 활동 감소(A) 참고 점수.

## 4. 점수 구조

### 4.1 구성요소 점수 c ∈ [0, 1]

이벤트 하나가 구성요소 하나다. 각 유형은 **기본값**(도착만으로 얻는 점수)과 **심화**(reason으로 얼마나 더 심한지)로 나뉜다. `clip`은 0~1 제한이다.

```text
무활동 I_ev
  over  = 깨어 있는 시간으로 잰 경과 − threshold_hours      (sleep_window 제외, 시간)
  c_I   = base_I + (1 − base_I) × clip(over / threshold_hours)
          → 임계의 두 배에서 1.0 (임계가 2시간인 예에서는 4시간)

장시간 사용 U_ev  (가전마다 하나, U = 최댓값)
  ratio = (now − started_at) / allowed_duration_minutes − 1
  c_U   = base_U + (1 − base_U) × clip(ratio)
          → 허용 시간의 두 배에서 1.0

루틴 미사용 M_ev  (가전마다 하나, M = 최댓값, 기본 가중치 0)
  p     = normal_days / window_days
  delay = clip((now − 오늘의 expected_until) / grace_M)
  c_M   = p × (base_M + (1 − base_M) × delay)
```

기본값 후보: `base_U = 0.6`, `base_I = 0.4`, `base_M = 0.3`, `grace_M = 60분`. 모두 정책 값이며 미검증이다.

무활동의 "깨어 있는 시간"은 분석 서비스와 같은 규칙으로 잰다. reason의 `inactivity_started_at`과 `sleep_window`를 사용하되, 시간대·자정 경계·수면 구간 처리 규칙을 분석과 일치시킨다. 단순 수신 시각부터 재지 않는다. 시간 단위는 계산 전에 통일하며, 임계나 허용시간이 0 이하이거나 필요한 reason이 없으면 제외한다.

`grace_M`은 알림 유예가 아니라 점수를 최대로 올리는 지연 구간이다. `normal_days/window_days`가 실제 유효 관측일의 사용 비율인지 계약을 확인해야 하며, 관측 누락일을 미사용일로 간주하지 않는다. M은 기본 제외이므로 활성화 전에 이 의미를 검증한다.

관측 공백·외출 이후에도 `now`만 증가시켜 위험을 심화하지 않는다. 연속 관측과 사건 지속을 확인할 수 있는 시각까지만 계산하고, 이후는 평가 불가 또는 마지막 관측값으로 표시한다. 분석이 이미 해제한 상황을 오래된 발생 이벤트로 계속 평가하지 않도록 활동 재개·가전 OFF와의 연결이 필요하다.

### 4.2 맥락 보정

| 상황 | 처리 | 근거 |
|---|---|---|
| 이벤트 발생 시각에 외출 중 | 무활동·루틴 미사용 구성요소 제외 | 지금의 알림 억제 규칙과 같다. 장시간 사용은 제외하지 않는다 |
| 이벤트 발생 시각에 기기 끊김 | 무활동·루틴 미사용 구성요소 제외 | 지금의 오경보 방지 규칙과 같다 |
| 대상자가 "예"(위험) 응답 | 그 구성요소 c = 1.0 | 본인이 위험하다고 답했다. 가장 강한 신호다 |
| 대상자가 "아니오"(괜찮음) 응답 | 그 구성요소 c × 0.3 | 지우지는 않는다. 담당자가 확인할 때까지 흔적은 남긴다 |
| 응답 기한 초과(무응답) | 실제 발송·응답 가능 상태를 확인한 경우에 한해 c에 +0.1 (clip), 그 외 보정 제외 | 발송 안 됨·실패를 사람의 무응답 위험으로 해석하지 않는다. SENT도 열람 보장은 아니다 |
| 담당자 조치 완료 | 구성요소 제거 | 지금의 슬롯 해제와 같다 |
| 가전 OFF / 최대 유지시간(6시간) 경과 | 구성요소 제거 | 지금의 슬롯 해제와 같다 |

보정 계수(0.3, +0.1)는 정책 값이다.

### 4.3 구성요소 결합 → 강도 R ∈ [0, 1]

기존 설계 11.2절의 결합식 형태를 후보로 사용한다. 이벤트 구성요소와 현재 A를 입력으로 쓰며, 전날 지수로 만든 A_day는 넣지 않는다.

```text
B = max(I_ev, M_ev, A)          부재 축. 서로 상관이 커서 더하지 않고 최댓값을 쓴다
U = max(가전별 U_ev)            가전 장시간 사용 축
R = min(1, max(B, U) + 0.1 × min(B, U))
```

- A(활동 감소 참고 점수, 0~1)를 B에 넣는 이유: 이벤트가 하나도 없는 정상 대상자끼리도 순서를 만들기 위해서다. A는 여전히 등급·알림을 만들지 않는다.
- 계수 0.1은 11.2절 그대로 미검증이다. "두 축이 다 걸린 사람이 한 축만 걸린 사람보다 앞에 온다"는 성질만 보장하면 된다.
- 두 축의 통계적 독립을 가정하지 않는다. 동시 활성 상태가 실제로 가능한지와 오래된 이벤트가 남은 결과인지 먼저 확인한다. 반올림·상한 때문에 동점은 가능하다.
- 유효 구성요소가 하나도 없으면 R과 비교 점수는 `null`이며, `UNAVAILABLE`로 표시한다. 빈 최댓값을 0으로 바꾸지 않는다. 일부만 유효하면 사용한 항목과 제외한 항목을 함께 남긴다.

### 4.4 등급 칸 안에 점수를 넣는다

등급과 점수가 어긋나면 화면이 "주의 · 95점"처럼 보인다. 그래서 **등급이 칸을 정하고, R이 칸 안의 위치를 정한다.**

```text
칸(level):  NORMAL [0, 69]   WARNING [70, 89]   DANGER [90, 100]
            (경계는 기존 warning-threshold=70, danger-threshold=90에서 온다)

score = lower + round((upper − lower) × R)
```

이러면 다음이 항상 성립한다.

- 위험 > 주의 > 정상. 등급이 다르면 점수로도 순서가 같다.
- 같은 등급 안에서는 R이 큰 사람이 앞이다.
- 기존 대표값(70, 90)은 각 칸의 하한이 된다. 기본 구성요소가 0보다 크므로 신규 이벤트의 비교 점수는 하한보다 높을 수 있다. 기존 대표 점수와 새 비교 점수는 다른 값이다.

정렬 키는 `(level desc, comparisonScore desc nulls last, 이벤트 최근 발생 시각 desc)`다. 유효 점수가 있으면 점수 구간이 등급 순서를 보장하지만, 점수가 없는 대상자의 등급과 동점 처리를 위해 정렬 키를 유지한다.

### 4.5 예시

| 상황 | 구성요소 | R | 등급 | 점수 |
|---|---|---|---|---|
| 무활동 2시간 10분 (막 넘김) | I = 0.4 + 0.6 × clip(0.17/2) = 0.45 | 0.45 | 주의 | 70 + round(19 × 0.45) = **79** |
| 무활동 5시간 | I = 0.4 + 0.6 × clip(3/2) = 1.0 | 1.0 | 주의 | **89** |
| 무활동 5시간, "아니오" 응답 | I = 1.0 × 0.3 = 0.3 | 0.3 | 주의 | **76** |
| 다리미 허용 2분, 3분째 | U = 0.6 + 0.4 × clip(0.5) = 0.8 | 0.8 | 위험 | 90 + round(10 × 0.8) = **98** |
| 다리미 3분째 + 무활동 3시간 | U = 0.8, I = 0.7 | min(1, 0.8 + 0.07) = 0.87 | 위험 | **99** |
| 이벤트 없음, A = 0.5 | B = 0.5 | 0.5 | 정상 | round(69 × 0.5) = **35** |
| 이벤트 없음, A 계산 불가 | 없음 | null | 정상 | **산정 불가** (근거에 `A: EXCLUDED`) |

## 5. 상태와 저장

### 5.1 활성 이벤트 표 (슬롯 하나 → 여러 개)

```sql
-- 설계 예시. 실제 마이그레이션 번호는 구현 시 미사용 번호로 배정한다.
CREATE TABLE subject_active_risk_events (
    subject_id     BIGINT      NOT NULL REFERENCES subjects(id),
    event_id       UUID        NOT NULL REFERENCES analysis_events(id),
    event_type     VARCHAR(50) NOT NULL,
    appliance_type VARCHAR(50),
    level          VARCHAR(20) NOT NULL,          -- 라우팅이 정한 등급
    set_at         TIMESTAMPTZ NOT NULL,
    response_effect VARCHAR(20),                  -- NONE | YES | NO | EXPIRED
    PRIMARY KEY (subject_id, event_id)
);
```

- 이벤트 도착: 행 추가. 같은 `(subject, event_type, appliance_type)`이 이미 있으면 새 것으로 바꾼다(재발송 방지는 지금처럼 `event_id`로).
- 해제 조건(연결된 가전 OFF, 해당 이벤트에 대한 담당자 조치 완료, 최대 유지시간)은 행 단위로 적용한다. 무활동은 활동 재개를 해제 근거로 연결하는 보완이 필요하다. **무응답 만료는 해제가 아니라 응답 상태 변경**이다.
- **등급**은 활성 행의 `level` 최댓값으로 제안한다. 현재는 단일 이벤트 슬롯을 새 이벤트가 덮어쓰므로 동시 사건에서는 결과가 달라진다. 이 전환은 별도 검증 대상이며 유형별 등급 라우팅 자체는 유지한다.
- 기존 `subjects.event_risk_*` 컬럼은 전환 기간에 "가장 높은 행"의 사본으로 유지하고, 프론트가 새 API로 넘어간 뒤 제거한다.

### 5.2 재계산 시점

지금 평가가 도는 시점과 같다: 이벤트 도착, 스냅샷의 가전 OFF, 대상자 응답, 담당자 조치, 1분 타이머. 타이머가 필요한 이유는 심화 항(경과 시간)이 시간의 함수라서다.

점수가 바뀔 때만 `state_version`을 올린다(지금 `applyAssessment`의 "같은 결과면 화면을 건드리지 않는다" 규칙 그대로).

### 5.3 근거 기록

`risk_assessments.indicators`에 구성요소 배열을 함께 남긴다. `score_version`은 `monitoring-score-v3-EV`로 올린다.

```json
{
  "components": [
    {"code": "I", "eventId": "…", "c": 0.7, "inputs": {"overHours": 1.0, "thresholdHours": 2}, "response": "NONE"},
    {"code": "U", "eventId": "…", "appliance": "IRON", "c": 0.8, "inputs": {"ratio": 0.5}},
    {"code": "A", "c": 0.5, "bucket": "12:00"},
    {"code": "M", "excludedReason": "WEIGHT_ZERO"}
  ],
  "B": 0.7, "U": 0.8, "R": 0.87, "level": "DANGER", "band": [90, 100], "score": 99
}
```

이 기록이 있어야 "왜 이 사람이 저 사람보다 위인가"를 담당자 화면과 보고서에서 설명할 수 있다.

## 6. 정책 값 (`app.risk.*`, `policy-v3-experimental`)

| 키 | 기본 | 뜻 |
|---|---|---|
| `component.base.inactivity` | 0.4 | 무활동 도착 시 기본 |
| `component.base.appliance-use` | 0.6 | 장시간 사용 도착 시 기본 |
| `component.base.routine-missed` | 0.3 | 루틴 미사용 기본 |
| `component.weight.routine-missed` | **0** | 루틴 미사용을 점수에 넣을지. 0이면 제외 |
| `component.routine-missed-grace` | 60m | 루틴 미사용 지연 기준 |
| `response.no-multiplier` | 0.3 | "아니오" 응답 보정 |
| `response.expired-bonus` | 0.1 | 무응답 가산 |
| `combine.secondary-weight` | 0.1 | 11.2절의 계수 |
| `warning-threshold`, `danger-threshold` | 70, 90 | 칸 경계 (기존 값 재사용) |

## 7. 검증 방법

- **단위**: 구성요소 함수마다 경계값(임계 직후 0.4, 두 배에서 1.0, 응답 보정)과 제외 사유.
- **성질**: 이벤트가 하나 더 걸리면 점수가 내려가지 않는다. 경과 시간이 늘면 내려가지 않는다. 등급이 높으면 점수가 항상 높다. 같은 입력이면 같은 점수다.
- **재생**: 과거 재평가 CLI(`historical-assessment`)에 활성 이벤트 재생을 붙여, 저장된 `analysis_events`·`notifications`로 며칠치 순위를 만들어 본다. 지금의 70/90 정렬과 비교해 순서가 뒤집히는 경우를 담당자와 함께 본다.
- **운영 그림자**: 1단계에서는 점수를 이력에만 남기고 화면에는 내보내지 않는다.

## 8. 단계

1. **계산기와 이력.** `EventRiskAggregator`(순수 계산기) + `risk_assessments`에 v3 근거 기록. 화면·API는 그대로.
2. **API와 정렬.** `SubjectSummary`에 `comparisonScore`를 추가하고 프론트 정렬을 이 값으로 바꾼다. 기존 `riskScore`는 유지.
3. **슬롯 → 활성 이벤트 표.** 신규 마이그레이션, 해제 로직을 행 단위로 이전, 호환 전환 완료 후 `event_risk_*` 컬럼 제거.
   실제 번호는 구현 시 정한다. 1·2단계의 다중 이벤트 계산은 이력 재생 또는 그림자 상태 저장으로 검증하며, 단일 운영 슬롯만으로 동시 이벤트를 복원했다고 보지 않는다. 운영 등급을 활성 행의 최댓값으로 바꾸는 시점은 이 단계다.

## 9. 하지 않는 것

- 점수를 확률로 해석하거나 설명하지 않는다.
- 이 점수로 알림을 내거나 등급을 올리지 않는다.
- 현재 reason을 우선 사용한다. 누락된 지속·해제 근거를 추정으로 채우지 않는다. 계약 보완이 필요하면 별도 변경으로 다룬다.
- 루틴 미사용을 기본으로 점수에 넣지 않는다.

## 10. 결정이 필요한 것

1. 활동 감소 A를 B에 넣을지. 넣으면 정상 대상자끼리 순서가 생기지만, "A는 참고값"이라는 말이 흐려진다.
2. "아니오" 응답의 보정 0.3이 적당한지. 0으로 두면 본인이 괜찮다고 하는 순간 목록에서 내려간다.
3. 무응답 가산 +0.1을 둘지. 응답 기한이 60초라 무응답이 흔할 수 있다.
4. 단일 슬롯에서 활성 이벤트 최댓값으로 전환할 때 등급·재알림을 어떻게 검증할지. 재알림의 assessment_id와 활성 이벤트 집합을 연결해야 응답 보정·조치 완료를 엉뚱한 이벤트에 적용하지 않는다.
5. 관측 공백 이후 점수의 유효기간, 무활동 해제 신호, 동종 이벤트 교체 기준을 무엇으로 할지.
6. 일일 활동 감소 A_day의 최소 유효 표본 수·외출일 처리·유효기간을 무엇으로 할지. 이 값의 도입은 현재 A 및 이번 비교 점수와 별도 후속 작업이다.
