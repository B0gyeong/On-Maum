# 과거 몇 달치 데이터 생성 방식 결정과 기간 구성 설계

- 정리일: 2026-09-24 (같은 날 기본안을 "규칙 세션 + 시뮬레이터 파형"으로 변경)
- 단계: 2단계(생성 방식 결정) 결론과 3단계(몇 달치 확장: 정상·변화·이상 기간 구성) 설계
- 목표: 과거 몇 달치 데이터를 레이크에 적재하고 Silver → Gold → 과거 위험 평가 → 보고서까지 집계했을 때 생활 패턴(기준선, 통계 프로필, 루틴 변화, 위험 점수)이 잡히는지 확인한다. 모델 정확도 측정이 목표가 아니다.
- 이 문서는 설계이며 저장소 코드·설정·DB를 변경하지 않았다. 실험 스크립트는 세션 scratchpad에서만 실행했다.

## 0. 결정 요약

레이크 입력은 원본 파형과 세션이 분리돼 있다. 가전별 사용량과 모든 패턴 지표는 세션에서만 나오고, 원본 파형은 관측 품질(수집률 0.95 기준 VALID/INSUFFICIENT_DATA)에만 쓰인다. 그래서 세션은 우리가 정한 규칙으로 직접 만들고, 파형은 수집률만 맞으면 된다.

| 층 | 결정 | 근거 |
|---|---|---|
| 세션 | 규칙 일정표로 생성. 가전별 시각 중앙값, 흔들림, 사용 확률, 지속시간, 요일 조건 | 우리가 넣은 패턴을 집계가 그대로 잡는지 보는 것이 목적이므로 정답을 직접 정한다. AI 모델과 무관하고 기간 제한이 없다 |
| 원본 파형(Bronze power) | 기존 시뮬레이터 물리 엔진을 MQTT 없이 함수로 호출해 1초 값 생성. 세션 일정에 맞춰 가전 ON/OFF를 수동 제어 | 가구·하루 1.2초로 생성. 파형은 수집률에만 쓰이므로 사실감이 집계 결과에 영향을 주지 않는다. 화면에서 원본을 봐도 자연스럽다 |
| 정상·변화·이상 기간 | 일정표 규칙의 시각 이동, 사용 삭제, 파형 결측 삽입으로 구성 | 4장 |
| 과거 위험 점수 | 일정표로 snapshot을 합성해 `historicalAssessment` 실행 | monitoring 실시간 경로는 `assessed_at`을 현재 시각으로 기록해 과거 날짜에 점수가 남지 않는다 |
| 전달 경로 | MQTT·Kafka 실시간 경로가 아니라 파일로 Bronze·receipt·세션을 직접 기록 | 실제 모델 Consumer 1개당 약 15 msg/s. 3개월 1가구 약 790만 건은 실시간 경로로 비현실적 |
| 모델 추론 | 몇 달치 생성에 사용하지 않음 | 2.1·2.2절. 합성 파형은 가전 간 혼동, 실측 파형은 하루 수십 분~두 시간의 오탐이 생겨 패턴이 잡음에 묻힌다 |
| AI Hub 실측 데이터 | 기본안에서 제외. 10장의 선택 사항으로만 유지 | 실측 라벨을 세션으로 쓰면 실제 사람 패턴이 들어오지만, 200GB 데이터셋·30Hz 변환·학습 가구 논의가 따라온다. 배치 검증에는 필요 없다 |

## 1. 확인한 전제

- 세션 → `appliance_usage_daily`의 규칙(0920 설계 7.2절): 전기포트·전자레인지·드라이어·청소기 병합 60초, 인덕션 120초, 다리미 300초, 유효 사용 10초 이상. 규칙 일정표는 이 규칙을 통과하도록 세션을 만든다.
- Gold 기준선(`gold-profile` 설정 기본값): 창 28일, 표본 14일 이상, 요일별 4일 이상, 일 사용확률 0.70 이상일 때 활성화. 시간대 통계는 30분 버킷.
- monitoring 위험 점수(`RiskProperties` 기본값): M(루틴 미사용)은 첫 사용 P90 경과 후 지연을 spread(P90-P50, 최소 30분)로 나눠 점수화. I(무활동 경과)·A(누적 시작 횟수)는 시간대별 P50/MAD 대비 z 2~6을 0~1로 매핑. 70 WARNING, 90 DANGER, 상승 유지 10분. 관측 커버리지 0.95 미만이거나 공백 120초 초과면 지표 제외.
- 관측 대상 설정(`observation_targets.json`)에 가구별 `sampling_interval_seconds`가 있어 1초와 10초 가구를 섞어도 수집률이 맞게 계산된다.
- e2e 테스트(`batch/gold_profile_service/tests/test_e2e_local_pipeline.py`)에 Bronze power·receipt·세션을 날짜별로 레이크에 직접 쓰는 작성기와 manifest 형식이 있고, 실제 Spark·PostgreSQL·Kafka·monitoring으로 6개 시나리오가 통과했다(0921 문서). 이번 도구는 그 형식을 그대로 따른다.

## 3. 가구 구성

가상 가구는 규칙 일정표로 정의한다. 시각·확률 값은 AI Hub 16가구 라벨에서 계산한 실제 루틴 통계를 참고했다(예: H105 전기포트 첫 사용 08:48, 사분위 08:36~09:48, 31일 중 31일 사용). 기준선이 활성화되려면 핵심 가전의 사용 확률이 0.70 이상이어야 한다.

| 가상 가구 | 성격 | 규칙 일정(중앙값 ± 흔들림, 사용 확률, 지속) | 참고한 실측 |
|---|---|---|---|
| H008 | 아침 루틴 가구 | 전기포트 08:50 ± 15분, 0.97, 3분, 하루 2~4회(추가 사용 12시·20시 0.6). 헤어드라이어 20:10 ± 30분, 0.9, 5분. 청소기 평일 12:20 ± 60분·주말 10:30 ± 60분, 0.8, 6분 | H105 |
| H009 | 저녁 인덕션 가구 | 인덕션 19:00 ± 20분, 0.9, 12분(듀티 사이클). 점심 12:10 ± 30분, 0.5, 8분. 다리미 월·수·금 12:30 ± 120분, 0.8, 6분 | H027 |
| H010 | 1인 가구 | 전자레인지 17:50 ± 60분, 0.94, 5분. 21:00 ± 60분, 0.5, 3분 | H082 |
| H007 (선택) | 6종 모두 쓰는 가구 | 전자레인지 05:55, 전기포트 13:00, 다리미 16:50, 청소기 20:20, 헤어드라이어 10:50, 인덕션 18:30 | H083 |

- 세션 지속시간은 가전별 범위에서 시드로 뽑는다. 병합 간격 안에서 끊기는 짧은 세션(인덕션 듀티 사이클)도 넣어 usage-daily 병합 규칙이 실제로 동작하는지 본다.
- 가구 ID는 로컬 monitoring DB(`subjects`)에 이미 등록된 `H001`~`H010` 중에서 고른다. `H001`~`H007`은 시뮬레이터 시연과 기존 프로필 데이터가 있으므로 비어 있는 `H008`~`H010`을 시연 가구로 쓴다. 관측 대상 설정 `observation_targets.json`에는 현재 `H001`~`H003`만 있어 `H008`~`H010`을 추가해야 한다(실행 시 `OBSERVATION_TARGETS_FILE`로 별도 파일을 넘기는 방식도 가능). 선택 가구 `H007`은 기존 데이터를 정리한 뒤에만 쓴다. 부하 가구 1,000곳은 `L0001`~`L1000`처럼 별도 접두어로 만들고 monitoring 등록 없이 Silver·usage·Gold까지만 측정한다.
- 일정표는 시드로 결정적이다. 같은 시나리오 JSON과 시드는 같은 세션을 만든다.

## 4. 기간 구성

### 4.1 전체 범위

- 대상 기간: 2026-06-25(목) ~ 2026-09-23(수), 91일(13주). 끝을 어제로 두면 `gold-profile daily`와 `household-report daily`가 기본 계약대로 돈다.
- 규칙 일정은 날짜마다 새로 뽑으므로 반복 구간이 없다. 요일 조건(주말 청소기 시각, 다리미 월·수·금)으로 요일별 기준선(WEEKDAY scope)도 채워진다.
- `measured_at`은 대상 날짜의 KST 자정부터 표본 간격으로 찍는다.

### 4.2 세 기간

| 기간 | 날짜 | 일수 | 규칙 변경 |
|---|---|---:|---|
| 정상 | 06-25 ~ 08-19 | 56 | 3장의 일정표 그대로. Gold 28일 창이 처음 차는 07-22부터 기준선 READY. 그 전 27일은 설계상 INPUT_INCOMPLETE(exit 10) |
| 변화 | 08-20 ~ 09-02 | 14 | 핵심 가전 1종의 시각 중앙값을 +150분 이동. H008 포트 08:50 → 11:20, H009 인덕션 19:00 → 21:30, H010 전자레인지 17:50 → 20:20 |
| 이상 | 09-03 ~ 09-23 | 21 | 4.3절의 소구간 |

변화 기간에서 볼 것은 두 가지다. 28일 창에 새 날이 들어오면서 기준선 첫 사용 P50이 서서히 이동하는지, 그 사이 M 지표가 어떻게 반응하는지다. 현재 정책으로는 평소 P90(약 09:50)을 지나 실제 사용(11:20)까지 매일 약 90분 동안 M 점수가 오르고, 지연이 spread를 넘으면 100점까지 간다. 즉 루틴 변화는 기준선이 따라잡기 전까지 위험으로 보인다. 숨길 일이 아니라 보고서에서 확인할 정책 특성이다.

### 4.3 이상 기간 소구간

| 소구간 | 날짜 | 규칙 변경 | 기대 결과 |
|---|---|---|---|
| 관측 결측 | 09-04 | 전 가구 파형 09:00~15:00 6시간 삭제(receipt도 삭제) | 수집률 0.75 → 관측일 INSUFFICIENT_DATA, usage UNKNOWN, baseline 제외, M·I·A 제외(REASON_OBSERVATION_COVERAGE) |
| 활동 감소 | 09-06 ~ 09-12 | H008·H010 가전별 하루 첫 사용만 남김 | usage_status USED 유지, usage_count 감소, A 지표 상승 |
| 외출 | 09-08 09:00~18:00 | H009 `awayPeriods`로 지정(데이터 변경 없음) | 그 시간대 M·I·A 제외(REASON_AWAY) |
| 장시간 사용 | 09-10 | H009 인덕션 저녁 세션 하나를 3시간으로 연장 | usage_minutes 급증. `PROLONGED_APPLIANCE_USE`는 실시간 경로 전용이므로 과거 점수에는 없음(문서화) |
| 무활동 | 09-13 ~ 09-16 | 전 가구 대상 가전 사용 확률 0 | usage NOT_USED 4일, M(P90 경과)·I(경과시간)·A(시작 0회) 상승, WARNING(70) 이상, 연속 시 DANGER(90) |
| 회복 | 09-17 ~ 09-23 | 변경 없음 | 점수 정상 복귀. NOT_USED 4일이 표본에 남아 daily_use_probability가 약간 하락 |

파형은 세션 일정에 맞춰 가전을 켜고 끄므로 세션과 파형이 항상 일치한다. 결측 편집은 파형과 receipt에, 나머지 편집은 일정표에 적용한다.

## 5. 산출물·실행 순서·구현

### 5.1 생성 산출물 (시연 3가구 91일 기준)

| 산출물 | 형식·위치 | 규모 |
|---|---|---|
| 세션 일정 | 시나리오 JSON → 가구·날짜별 논리 사용 목록(중간 산출, 정답표) | 가구·일당 수 건 |
| Bronze power | e2e `write_bronze_power`와 같은 스키마·manifest. `ingest_date=대상일`, 날짜·시간·파티션 단위 파일에 가구를 합침, 1초 간격 | 약 2,360만 행, 약 1.1GB |
| 분석 receipt | 입력 1건당 SUCCEEDED 1건, `analysis_run_id` 고정. 결측 초는 receipt 없음. 날짜당 배치 1개 | Bronze와 동일 건수 |
| 세션 Bronze | 논리 사용 구간을 INSERT 버전 1로. `session_id`는 가구·가전·시작시각 해시로 결정적. `max_probability` 0.99, `decision_threshold`는 프로파일 값. 날짜당 배치 1개 | 가구·일당 수 건 |
| snapshot | `analysis.snapshot.v1` 형식, 60초 간격(관측 공백 기준 120초 미만), 일정표로 `is_on`, 파형으로 measurement | 가구당 약 13.1만 줄 |
| Gold 프로필 메시지 | 날짜별 `gold-profile daily` 뒤 `gold_profile_delivery_outbox` payload 수집 → `profiles.json` | 가구당 최대 64건(07-22 이후) |
| 과거 평가 | `historicalAssessment` 결과 → `import-assessments` → `--historical-manifest` | 가구당 1회 |

receipt는 e2e와 같이 전 입력 SUCCEEDED로 단순화한다. 실제 서비스라면 첫 254초는 SKIPPED_WARMUP이지만 하루 단위 분석 커버리지에는 무시할 수준이다.

### 5.2 실행 순서

1. 시나리오 JSON 확정. `plan`으로 가구·날짜별 일정표와 편집 적용 결과를 표로 출력해 검토한다.
2. `write --from 2026-06-25 --to 2026-09-23`: 날짜 순서로 파형 생성 → Bronze power·receipt·세션 Bronze·manifest 기록. 시연 3가구는 약 6분.
3. `observation_targets.json`에 가구 추가, 로컬 analysis DB에 필요한 테이블 확인, monitoring에 가구 등록.
4. 날짜별 `gold-profile daily --as-of D --no-publish`를 06-25부터 09-23까지 오래된 날부터 실행. 07-21까지는 exit 10이 정상이고 Silver·usage만 남는다. 로컬 e2e 기준 날짜당 1~2분, 전체 2~3시간.
5. `profiles`로 outbox payload를 모아 가구별 `profiles.json`, `snapshots`로 `snapshots.jsonl`, `policy.json`(현재 기본값, `policyVersion` 명시), `config.json`(외출 구간 포함)을 만들고 `historicalAssessment` 실행.
6. `import-assessments` → `household-report daily --as-of 2026-09-23 --window-days 90 --historical-manifest ...` → Grafana 확인.

### 5.3 구현

새 도구 하나를 추가한다. 저장소 기존 코드는 수정하지 않는다. 위치는 `batch/history_generator/`(다른 batch 서비스와 같은 구조)이며 2026-09-24에 구현했다. 사용법은 그 디렉터리의 README를 따른다.

| 명령 | 내용 |
|---|---|
| `plan` | 시나리오 JSON 검증, 가구·날짜별 일정표·편집 결과 출력 |
| `write` | 날짜 범위의 파형 생성과 Bronze power·receipt·세션·manifest 기록. 날짜 단위 멱등(`--force`로만 재기록) |
| `snapshots` | 일정표·파형 → `snapshots.jsonl` |
| `profiles` | outbox payload → `profiles.json` |
| `run-dates` | 날짜별 `gold-profile daily` 반복 실행과 exit code 기록 |

- Python 3.11, pyarrow·numpy. Spark는 쓰지 않는다. 레이크 기록은 `power_silver.storage`(로컬 파일 레이크·HDFS 모두 지원, e2e가 검증한 경로)를 재사용하고, 스키마는 `power_silver.schemas.BRONZE_POWER_SCHEMA`, e2e의 `SESSION_SCHEMA`, receipt 컬럼을 그대로 따른다.
- 파형은 `infrastructure/mqtt/simulator/engine`을 import해 `init_simulation_states`(가구별 시드) → 매초 `calculate_main_panel_metrics(allow_random=False)`로 만들고, 일정표의 시작·종료 시각에 `set_manual_device_state`로 가전을 켜고 끈다. 시뮬레이터 코드는 수정하지 않는다.
- 실행은 e2e와 같이 `nilm-gold-profile:test` 이미지를 `nilm-net`에 붙여 컨테이너 안에서 한다. 시뮬레이터 디렉터리는 읽기 전용 마운트한다.
- 시각 문자열은 날짜당 한 번 만들어 가구 간 재사용한다.
- 시나리오 JSON 구조: 전체 공통은 `range`(시작·종료 날짜)와 기록 대상만이다. 나머지는 모두 `households[]` 안에 둔다. 가구 ID, 표본 간격, 시드, `schedule[]`(가전, 요일, 시각 중앙값, 흔들림 분, 사용 확률, 지속 범위, 추가 사용), `periods[]`(날짜 범위, 규칙 변경: 시각 이동, 확률 덮어쓰기, 첫 사용만 유지, 파형 결측 구간), `away[]`. 따라서 변화 폭·이상 종류·날짜를 가구마다 다르게 줄 수 있다. 예: H008은 08-20~09-02 포트 +150분과 09-13~09-16 무활동, H009는 08-27~09-02 인덕션 +90분과 09-08 외출·09-10 장시간 사용, H010은 09-04 결측과 09-06~09-12 활동 감소. 4.2·4.3절의 표는 이 배치를 모든 가구에 같이 적용한 기본안이다.
- 예상 작업량: 도구 1일, 실행·검증 0.5일.

## 7. 제약과 확인 요청

- 과거 점수는 `EVENT_TIME_REASSESSMENT`이며 당시 히스테리시스·알림 이력의 복원이 아니다(docs/historical-assessment.md).
- `PROLONGED_APPLIANCE_USE`, `ROUTINE_CHANGED`, `DATA_GAP`은 실시간 분석 서비스 이벤트라 이 경로에는 나오지 않는다.
- 로컬 `realtime-analysis-service`는 alembic revision 충돌(0921 P1-1)로 기동하지 않을 수 있다. 이 경로는 실시간 서비스를 쓰지 않지만 analysis DB 테이블은 필요하므로 e2e처럼 `Base.metadata.create_all` 또는 수정된 마이그레이션이 전제다.
- 이 경로는 monitoring 실시간 평가를 거치지 않으므로 실제 알림은 나가지 않는다. Gold를 ACTIVE로 발행하면 로컬 monitoring 프로필이 바뀌므로 `--no-publish`로 둔다.
- 운영 데이터에는 정답 라벨이 없으므로 운영의 가전별 세션은 실시간 모델이 만든다. 이 도구는 테스트 데이터 생성용이다. 운영에서 모델과 무관하게 집계할 수 있는 것은 수집 품질과 총 전력 통계이며, 총 전력 기반 Gold 집계는 현재 없다(별도 과제).
- 계절 패턴·대상자 특성 비교는 현재 Gold(가구 안의 28일 창 기준선)에 없다. 월별·계절 집계와 가구 속성 코호트 집계는 별도 과제다.

## 9. 1,000가구 부하 테스트 확장

### 9.1 어느 경로의 부하인가

| 경로 | 1,000가구 × 1Hz 가능 여부 | 근거 |
|---|---|---|
| 실시간 추론(MQTT → Kafka → 실제 모델 → 세션) | 로컬 불가 | 실제 모델 Consumer 1개당 약 15 msg/s(0922 측정). 1,000 msg/s는 Consumer 약 67개. FakePredictor도 80가구에 4개가 필요해 1,000가구는 약 50개 |
| 수집 경로만(시뮬레이터 → bridge → Kafka → bronze-loader) | 가능(시뮬레이터 설계 목표) | 모델 Consumer를 끄고 수집·적재 처리량만 본다. 이 문서 범위 밖 |
| 레이크 집계 배치(Bronze → Silver → usage → Gold → 보고서) | 가능, 표본 간격·일수로 규모 조절 | 9.2 |

이 문서의 부하 테스트는 레이크 집계 배치 경로다. 날짜별 `power-silver run`, `usage-daily`, `gold-profile run`, `household-report daily`의 실행 시간과 파일 수, Spark 메모리를 가구 수 10 → 100 → 1,000 순서로 측정한다.

### 9.2 규모 산정 (1Hz 하루 86,400행 = snappy 4.1MB, zstd 2.1MB)

| 구성 | Bronze 행 | Bronze 크기 | receipt 포함 추정 | 판정 |
|---|---:|---:|---:|---|
| 3가구 × 91일 × 1Hz | 2,360만 | 1.1 GB | 약 2 GB | 시연 가구 |
| 100가구 × 91일 × 1Hz | 7.9억 | 38 GB | 약 70 GB | 로컬 가능 |
| 300가구 × 28일 × 1Hz | 7.3억 | 35 GB | 약 65 GB | 로컬 가능, Gold 창 1개 |
| 1,000가구 × 28일 × 1Hz | 24억 | 116 GB | 약 200 GB | 로컬 한계(호스트 여유 약 280 GB, Silver 산출물 별도) |
| 1,000가구 × 91일 × 1Hz | 79억 | 377 GB | 약 700 GB | 로컬 불가 |
| **1,000가구 × 91일 × 10초 간격** | 7.9억 | 38 GB | 약 70 GB | **기본안** |

- 10초 간격은 `observation_targets.json`의 `sampling_interval_seconds`로 가구별 지정해 Silver 수집률 계산이 그대로 맞는다. 시연 가구는 1Hz, 부하 가구는 10초로 섞는다.
- 로컬 HDFS는 Docker 가상 디스크 기준 842 GB 여유로 보이지만 실제 호스트 여유는 약 280 GB다. Docker 자원은 8 CPU, 16 GB다.
- 파일 수: 가구·일별 파일로 쓰면 91,000개가 생겨 Spark 작은 파일 문제가 난다. 실제 bronze-loader 배치 형태대로 날짜·시간·파티션 단위 파일에 여러 가구를 합쳐 쓴다. receipt·세션도 날짜당 배치 1개.
- 파형 생성 시간: 시뮬레이터 엔진은 가구·하루 1.2초라 1,000가구 91일을 개별 생성하면 단일 프로세스 약 30시간이다. 부하 가구는 엔진으로 만든 파형 풀(예: 시드 다른 50가구·일)을 가구 ID·시각만 바꿔 재사용한다. 파형은 수집률에만 쓰이므로 결과에 영향이 없다.

### 9.3 1,000가구를 만드는 방법

- 부하 가구 일정표는 3장의 세 가구 유형을 원형으로 두고 시드로 시각 중앙값 ±60분, 사용 확률 ±0.1을 흔들어 만든다. 유형 비율은 1인 가구 5, 아침 루틴 3, 저녁 루틴 2.
- 부하 가구는 정상 기간만 둔다. 무작위 5%에 무활동 4일을 넣어 보고서에 위험 가구가 섞이게 할 수 있다.
- `historicalAssessment`는 가구별 실행이므로 시연 가구에만 돌린다. 부하 가구는 Gold와 보고서까지가 부하 대상이다.
- monitoring 가구 등록은 보고서가 `risk_assessments`를 읽을 때만 필요하므로 부하 가구는 등록하지 않아도 Silver·usage·Gold 부하 측정은 가능하다. 보고서까지 보려면 1,000가구 등록 스크립트가 필요하다.

### 9.4 측정 항목

| 단계 | 측정 | 기대 병목 |
|---|---|---|
| Bronze 기록 | 가구·일당 시간, 총 크기, 파일 수 | 디스크 |
| `power-silver run` (날짜당) | 실행 시간, 셔플 파티션, 실행기 메모리 | 1Hz 8,640만 행/일에서 Spark local 메모리 |
| `usage-daily` | 세션·receipt 조인 시간 | receipt 건수 |
| `gold-profile run` | 28일 창 읽기 시간, 가구 수 대비 선형성 | 창 28일 × 가구 수 |
| `household-report daily` | 보고서 생성·DB 게시 시간, `report_rows` 건수(1,000가구 × 91일 × 가전 6 ≈ 55만 행) | PostgreSQL 삽입 |
| Grafana | 가구 선택·패널 조회 응답 | `reporting` 뷰 인덱스 |

가구 수를 10 → 100 → 1,000으로 올리며 같은 날짜 3개를 반복 측정하고, 선형에서 벗어나는 단계를 기록한다.

### 9.5 분산 처리 검증

- 집계 배치(`power-silver`, `gold-profile`)는 Spark 코드지만 저장소 compose(local, ec2-b, hdfs)에는 Spark master·worker가 없어 컨테이너 안 `local[*]` 단일 노드로 돈다. 로컬 HDFS도 datanode 1개다. 이 상태의 측정은 로직·용량 검증이며 분산 검증이 아니다.
- 코드의 `SPARK_MASTER`(`POWER_SILVER_SPARK_MASTER`) 설정으로 외부 Spark standalone 클러스터를 지정하면 같은 잡이 여러 worker에 분산된다.
- 집계용 Spark 클러스터는 새로 준비해야 한다. EC2에 master·worker를 올리거나 PC 여러 대로 구성한다. 9월 초 AI 학습 데이터 전처리에 쓴 클러스터는 용도가 달라 그대로 "집계 클러스터"가 아니며, 그 장비를 빌려 다시 올리는 것은 수단의 선택일 뿐이다.
- 검증 방법: 같은 1,000가구 데이터의 같은 날짜 3개를 local 모드와 클러스터 모드로 각각 실행해 단계별 시간, 셔플 파티션 수, 실행기 메모리, worker별 task 편차를 비교한다. Bronze 파일 배치는 두 모드에서 동일하게 둔다.
- 검증 대상은 `power-silver run`, `usage-daily`, `gold-profile run`이다. `household-report daily`의 DB 게시는 단일 트랜잭션이라 분산 대상이 아니다.
- 선행 과제: 집계용 클러스터를 누가 어디에 올릴지.
