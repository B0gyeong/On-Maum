# 시뮬레이터 BURST·배속·시나리오 처리 정리

> 작성일: 2026-09-21  
> 대상: `infrastructure/mqtt/simulator`의 결정적 E2E 시뮬레이터  
> 목적: BURST와 배속 실행의 차이, 시나리오가 MQTT 데이터로 변환되는 과정, 운영 시 주의사항을 현재 구현 기준으로 정리한다.

## 1. 전체 구조 요약

현재 시뮬레이터에는 성격이 다른 두 실행 경로가 있다.

| 구분 | 기존 웹 시연 경로 | 결정적 E2E 경로 |
|---|---|---|
| 시작 API | `POST /api/start` | `POST /api/e2e/runs` |
| 주요 목적 | 파형 시연, 수동 제어 | AI·데이터 파이프라인 검증 |
| 시나리오 | `peak`, `normal_routine`, `routine_missed`, `sensor_fault`, `random`, `manual` | `ACTIVITY_*`, `ROUTINE_CHANGED_*`, `BASELINE_MICROWAVE_20D` 총 10종 |
| 속도 설정 | `interval` 또는 `POST /api/speed` | `execution.mode`와 `execution.speed` |
| 재현성 | 일부 확률 기반 | 동일 시나리오·날짜·가구이면 동일한 전력 파형 |
| 일자별 완료 결과 | 없음 | `day_results` 제공 |

두 경로는 동시에 실행할 수 없다. 기존 시뮬레이터 실행 중 E2E 실행을 시작하거나, E2E 실행 중 기존 시뮬레이터를 시작하면 HTTP 409로 거절한다.

이번 BURST·배속·시나리오 처리는 주로 **결정적 E2E 경로**에 해당한다.

## 2. 처리 흐름

```text
POST /api/e2e/runs
        │
        ├─ 요청 검증
        │   ├─ reference_date
        │   ├─ 실행 모드(REALTIME / ACCELERATED / BURST)
        │   └─ 가구 및 시나리오(최대 10가구)
        │
        ├─ 시나리오 카탈로그 조회
        │   └─ ScenarioDefinition
        │
        ├─ 실행 계획 컴파일
        │   └─ CompiledExecutionPlan
        │       ├─ 가상 날짜 범위
        │       ├─ ON/OFF 전환 시점
        │       ├─ 발행 슬롯
        │       └─ 의도적 결측 슬롯
        │
        ├─ 가구별 DeterministicScheduleExecutor 생성
        │
        └─ 매 가상 1초 슬롯 처리
            ├─ 가전 ON/OFF 상태 반영
            ├─ 물리 계측값 생성
            ├─ 결측이면 MQTT 발행 생략
            ├─ 정상이면 MQTT QoS 1 발행
            └─ 실행 모드에 따라 다음 슬롯까지 대기
```

핵심은 **실행 속도와 가상 시간이 분리**되어 있다는 점이다. 실제로 0.001초 만에 다음 메시지를 발행하더라도 `measured_at`과 `ts`는 항상 가상 시간 기준으로 1초씩 증가한다. 따라서 다운스트림에서는 REALTIME, ACCELERATED, BURST 중 어떤 모드로 발행했는지 알 필요 없이 정상적인 1 Hz 시계열로 처리할 수 있다.

## 3. BURST 처리 방식

### 3.1 동작 원리

BURST는 여러 샘플을 하나의 MQTT 메시지로 묶는 배치 전송이 아니다. 각 가상 1초 슬롯을 순서대로 생성하고, 정상 슬롯마다 기존과 동일한 MQTT 메시지 한 건을 발행한다.

다른 모드와의 차이는 슬롯 사이의 페이싱 대기를 제거한다는 것뿐이다.

```python
if mode == BURST:
    return  # 다음 슬롯까지 sleep하지 않음
```

따라서 다음 조건은 그대로 유지된다.

- 하루는 항상 86,400개의 가상 슬롯으로 처리한다.
- MQTT 메시지는 슬롯당 최대 1건이다.
- `measured_at`과 `ts`는 1초씩 단조 증가한다.
- 토픽은 `v1/power/sim/{household_id}/main`이다.
- QoS 1, `retain=False`로 발행한다.
- 발행 성공을 확인한 뒤 다음 슬롯을 처리한다.
- 계획된 결측 슬롯은 MQTT I/O, UUID 생성, JSON 직렬화를 모두 생략하고 `OMITTED` 수만 증가시킨다.

즉, BURST는 **샘플 수나 시간축을 줄이지 않고 wall-clock 대기만 제거한 최고속 순차 스트리밍**이다.

### 3.2 화면 처리

BURST는 데이터 발행 속도가 브라우저가 그릴 수 있는 속도보다 훨씬 빠르므로 SSE 파형 브로드캐스트를 하지 않는다. 실행 상태와 최종 발행 건수는 E2E 상태 조회 API로 확인해야 한다.

### 3.3 장점과 주의점

단일 일자 시나리오를 가장 빠르게 검증할 때 유용하다. 다만 MQTT 발행 완료와 Kafka 최종 적재 완료는 같은 의미가 아니다.

현재 MQTT-Kafka Bridge는 Kafka 확인 이후 MQTT ACK를 반환하지만 이 흐름이 시뮬레이터 발행자까지 완전한 백프레셔로 이어지지 않는다. 발행 속도가 Bridge 처리량보다 빠르면 Mosquitto의 송신 큐에 데이터가 누적되고, 큐를 넘으면 유실될 수 있다.

현재 로컬 실측 기준은 다음과 같다.

- Bridge 실효 처리량: 약 1,477건/초
- 안전 목표 합계 속도: 1,200건/초
- Mosquitto 설정: `max_inflight_messages 1000`, `max_queued_messages 100000`
- 단일 일자와 20일 BURST는 무손실을 확인했지만, 28일 시나리오는 큐 한계에 가까워 자동 배속 사용을 권장한다.

Mosquitto 큐 설정은 설정 파일만 수정해서는 적용되지 않으며 브로커 재시작이 필요하다.

### 3.4 BURST 유실 실측 결과

저장소에 남아 있는 로컬 E2E 실측 결과는 다음과 같다. 최적화 전 기록은 테스트 시점의 Bridge 병목 제거 여부와 Broker 설정 적용 상태가 서로 달라 수치가 두 가지이므로, 같은 조건의 반복 측정값으로 보면 안 된다.

#### 최적화 전

| 조건 | 시뮬레이터 발행 | Kafka 도달 | 유실 | 도달률 | 유실률 |
|---|---:|---:|---:|---:|---:|
| Mosquitto 기본 큐(`queued=1,000`, `inflight=20`) + Bridge 200ms 병목 | 86,400건 | 6,440건 | **79,960건** | 7.5% | **92.5%** |
| 큐 증설 설정이 실제 Broker에 반영되지 않은 후속 측정 | 86,400건 | 정확한 건수 기록 없음 | 정확한 건수 기록 없음 | **56.4%** | **43.6%** |

첫 번째 측정에서는 시뮬레이터가 정상적으로 86,400건 발행 완료를 보고했음에도 Kafka에는 6,440건만 도착했다. 즉, 시뮬레이터의 `published_samples`만으로 종단간 무손실을 판단할 수 없다는 점을 확인했다.

두 번째 56.4% 측정은 문서에 백분율만 남아 있어 건수를 역산해 확정값처럼 사용하지 않는다. 두 결과 모두 Broker 큐가 실제 운영 프로세스에 적용되지 않으면 대량 유실이 발생할 수 있음을 보여준다.

#### 최적화 후

아래 결과는 Bridge의 200ms 병목을 제거하고, Broker를 `max_inflight_messages 1000`, `max_queued_messages 100000` 설정으로 **재시작한 뒤** 측정한 값이다.

| BURST 조건 | 총 발행 | 실측 합계 속도 | Kafka 도달 | 유실 | 도달률 |
|---|---:|---:|---:|---:|---:|
| 1가구 × 1일 | 86,400건 | 1,476건/초 | 86,400건 | **0건** | **100%** |
| 2가구 × 1일 | 172,800건 | 2,037건/초 | 172,800건 | **0건** | **100%** |
| 3가구 × 1일 | 259,200건 | 2,703건/초 | 259,200건 | **0건** | **100%** |
| 1가구 × 20일 | 1,728,000건 | 1,541건/초 | 1,728,000건 | **0건** | **100%** |

따라서 현재 구성에서 실측으로 확인한 범위는 다음과 같이 해석해야 한다.

- **최대 순간 실측 무손실 속도:** 합계 약 2,703건/초, 단 3가구 × 1일의 유한한 실행에서 확인한 값이다.
- **최장 실측 무손실 실행:** 1가구 × 20일, 1,728,000건을 합계 약 1,541건/초로 발행해 유실 0건을 확인했다.
- 2,703건/초가 장시간에도 안전한 지속 가능 속도라는 의미는 아니다. Bridge 처리량을 초과한 데이터가 100,000건 Broker 큐에 임시로 쌓였기 때문에 짧은 실행이 통과한 것이다.
- 28일 BURST는 예상 백로그가 큐 한계인 약 100,000건에 도달하므로 무손실을 보장하거나 실측 완료한 구간으로 보지 않는다.

### 3.5 몇 배속까지 유실 없이 사용할 수 있는가

운영 권장 상한은 **전 가구 합계 1,200배속, 즉 약 1,200건/초**이다. Bridge 실효 처리량 약 1,477건/초보다 약 19% 낮게 잡아 Broker 큐가 계속 증가하지 않도록 한 값이다.

```text
합계 목표 속도 = 가구 수 × 가구당 speed
무손실 권장 조건 = 가구 수 × speed ≤ 1,200
가구당 자동 speed = 1,200 / 가구 수
```

| 동시 가구 수 | 가구당 권장 최대 배속 | 합계 속도 | 장시간 무손실 판단 |
|---:|---:|---:|---|
| 1 | 1,200배 | 1,200건/초 | 권장 |
| 2 | 600배 | 1,200건/초 | 권장 |
| 3 | 400배 | 1,200건/초 | 권장 |
| 5 | 240배 | 1,200건/초 | 권장 |
| 10 | 120배 | 1,200건/초 | 권장 |

여기서 말하는 1,200배속은 **가구별 배속의 합계**이다. 예를 들어 3가구를 각각 1,200배속으로 실행하면 합계는 3,600건/초이므로 안전 기준을 넘는다. 3가구일 때는 각각 400배속으로 설정해야 합계 1,200건/초가 된다.

실측 BURST에서 합계 2,703건/초까지 유실이 없었던 것과 장시간 권장 상한 1,200건/초는 모순이 아니다. BURST의 초과분은 Broker 큐가 임시로 흡수하지만, 1,200건/초는 Bridge 처리량보다 낮아 실행 시간이 길어져도 큐 누적 자체가 발생하지 않는 기준이다.

```text
예상 큐 누적량 ≈ max(0, 발행 속도 - 1,477) × 발행 시간
예상 큐 누적량이 100,000건에 가까워지면 유실 위험 구간
```

정리하면 다음과 같다.

- **장시간 실행의 무손실 권장값:** 합계 1,200배속 이하
- **실측된 단기 BURST 무손실 최고치:** 합계 약 2,703건/초(3가구 × 1일)
- **실측된 장기 BURST 무손실 구간:** 1가구 × 20일, 약 1,541건/초
- **검증되지 않은 구간:** 28일 BURST 및 합계 1,200건/초를 초과하는 임의의 장시간 실행

### 3.6 유실 확인 방법

실행 전후 Broker의 누적 드롭 카운터를 비교한다.

```bash
docker exec mosquitto-broker mosquitto_sub \
  -h localhost \
  -u simulator_user \
  -P test1234 \
  -t '$SYS/broker/publish/messages/dropped' \
  -C 1
```

정상 판정 조건은 다음 세 값을 함께 만족하는 것이다.

1. 시뮬레이터의 `published_samples == planned_publish_samples`
2. Broker dropped counter가 실행 전후 증가하지 않음
3. Kafka 고유 `message_id` 수가 `planned_publish_samples`와 일치함

PowerShell에서는 `$SYS`가 변수로 치환되지 않도록 위 토픽 문자열에 작은따옴표를 유지해야 한다.

## 4. 배속 처리 방식

### 4.1 E2E 실행 모드

| 모드 | 슬롯 간 목표 간격 | 특징 |
|---|---:|---|
| `REALTIME` | 1초 | 가상 1초를 실제 1초로 실행 |
| `ACCELERATED` | `1 / speed`초 | 지정 배속으로 실행 |
| `BURST` | 0초 | 의도적인 대기 없이 실행 |

예를 들어 `speed=10`이면 가상 시간 1초를 실제 약 0.1초마다 발행한다. `speed=1200`이면 가구당 목표 속도는 초당 약 1,200슬롯이다.

ACCELERATED와 REALTIME은 단순히 매 회 `sleep(간격)`을 호출하지 않는다. 실행 시작 시점의 `monotonic clock`을 기준점으로 잡고 다음 슬롯의 목표 마감 시각을 계산하여 기다린다.

```text
목표 시각 = 페이싱 기준 시각 + (처리 슬롯 수 + 1) × 슬롯 간격
대기 시간 = 목표 시각 - 현재 monotonic 시각
```

한 슬롯의 계산이나 MQTT 발행이 조금 늦어져도 다음 sleep에서 차이를 보정하므로, 처리 시간이 계속 누적되어 전체 실행이 점점 밀리는 현상을 줄인다. 이미 목표 시각을 지났다면 추가 대기 없이 다음 슬롯을 처리한다.

일시정지 후 재개할 때는 페이싱 기준점을 새로 설정한다. 따라서 정지해 있던 실제 시간을 따라잡기 위해 메시지를 한꺼번에 발행하지 않고, 중단된 가상 시각 다음 슬롯부터 설정된 속도로 이어간다.

### 4.2 자동 안전 배속

REST API에서 ACCELERATED 모드의 `speed`를 생략하면 가구 수를 기준으로 안전 배속을 자동 계산한다.

```text
가구당 speed = 1,200 / 실행 가구 수
전체 목표 발행 속도 = 약 1,200건/초
```

| 동시 실행 가구 수 | 가구당 자동 배속 | 전체 목표 속도 |
|---:|---:|---:|
| 1 | 1,200배 | 1,200건/초 |
| 2 | 600배 | 1,200건/초 |
| 3 | 400배 | 1,200건/초 |
| 10 | 120배 | 1,200건/초 |

자동 배속은 긴 시나리오에서도 Broker 큐 누적을 방지하기 위해 Bridge 실효 처리량보다 낮게 잡은 값이다. 계산된 값은 상태 조회 응답의 `speed_multiplier`에서 확인할 수 있다.

`speed`를 명시하면 자동 계산은 적용되지 않는다. 현재 서버는 0보다 큰 유한한 숫자인지만 검사하므로, 지나치게 큰 값을 직접 지정하면 BURST와 비슷한 유실 위험이 생길 수 있다.

### 4.3 기존 웹 시연 배속과의 차이

기존 `/api/start` 경로는 `interval`을 사용하며 허용 범위는 0.1~10초이다. `speed = 1 / interval` 관계이고 실행 중 `POST /api/speed`로 동적 변경할 수 있다.

E2E 경로의 `execution.speed`는 해당 런을 시작할 때 고정된다. 가구별 pause/resume/stop은 지원하지만 E2E 런의 배속을 실행 중 변경하는 API는 없다.

## 5. 시나리오 처리 방식

### 5.1 선언 계층

시나리오는 다음 세 단계로 선언된다.

```text
ScenarioDefinition
└─ DaySchedule
   ├─ ApplianceEvent
   │   ├─ appliance
   │   ├─ start_time
   │   └─ duration_seconds
   └─ OmissionRange
       ├─ start_second (포함)
       └─ end_second (미포함)
```

선언 시 다음 규칙을 검증한다.

- 시나리오 ID는 대문자 스네이크 케이스여야 한다.
- 날짜의 `day_offset`은 중복 없이 연속되어야 한다.
- 가전 이벤트는 최소 3초 이상이어야 한다.
- 이벤트 전후로 각각 최소 3개의 OFF 샘플을 확보해야 한다.
- 같은 가전의 이벤트는 겹칠 수 없고 이벤트 사이에 최소 3초의 OFF 구간이 있어야 한다.
- 이벤트의 전후 보호 구간과 의도적 결측 구간이 겹칠 수 없다.
- `publish_samples` 선언값과 `86,400 - 결측 수`가 일치해야 한다.

### 5.2 컴파일 계층

API의 `reference_date`는 시나리오의 시작일이 아니라 **마지막 날**이다.

```text
base_date = reference_date - (total_days - 1)
```

예를 들어 `reference_date=2026-09-21`이면 다음과 같이 계산된다.

| 시나리오 기간 | 실제 가상 날짜 범위 |
|---:|---|
| 1일 | 2026-09-21 |
| 20일 | 2026-09-02 ~ 2026-09-21 |
| 28일 | 2026-08-25 ~ 2026-09-21 |

`compile_schedule()`은 선언을 실행 가능한 불변 계획으로 변환한다. 모든 초의 객체를 미리 86,400개 또는 수백만 개 생성하지 않고, ON/OFF 전환은 sparse mapping으로 저장하고 가상 시각은 cycle에서 산술 계산한다. 그래서 20일·28일 시나리오도 전체 슬롯 수에 비례하는 대형 배열 없이 처리한다.

동일 초에 OFF와 ON이 함께 있으면 OFF를 먼저 적용한 뒤 ON을 적용한다.

### 5.3 런타임 계층

각 가구는 독립된 실행기와 난수 생성기를 가진다. 매 cycle에서 다음 순서로 처리한다.

1. 해당 cycle의 가전 ON/OFF 전환을 적용한다.
2. 기저부하, 냉장고, 활성 가전 상태로 P/Q/S/PF/V/I를 계산한다.
3. 현재 cycle이 발행 대상인지 결측 대상인지 판정한다.
4. 발행 대상이면 14필드 MQTT 페이로드를 만들고 QoS 1로 발행한다.
5. 결측 대상이면 외부 I/O 없이 `OMITTED`로 확정한다.
6. 발행·결측 카운터와 현재 날짜 진행 상태를 갱신한다.
7. 날짜 마지막 슬롯이면 계획 수와 실제 수가 일치하는지 확인하고 `day_results`를 확정한다.
8. 전체 종료 시 전체 발행 수, 결측 수, 처리 슬롯 수를 다시 검증한 후 `COMPLETED`로 전이한다.

발행 중 예외가 발생하면 해당 `pending_tick`을 지우지 않으므로 실패한 슬롯을 건너뛰지 않는다. 완료 상태는 계획된 샘플 수와 실제 확정 수가 모두 일치해야만 설정된다.

### 5.4 결정성 범위

가구별 난수 시드는 시나리오, 시작·종료 날짜, 전체 슬롯 수, 가구 ID를 기반으로 만든다. 따라서 같은 시나리오·날짜·가구 조합은 같은 물리 파형을 재현한다.

다만 MQTT `message_id`는 `(run_id, household_id, cycle, measured_at)` 기반 UUIDv5이다. 같은 런 안에서 동일 슬롯을 재시도하면 같은 ID가 나오지만, 새 런은 `run_id`가 달라지므로 같은 날짜를 다시 실행해도 다른 `message_id`가 생성된다.

시나리오 ID나 활성 가전 목록 같은 정답 라벨은 MQTT 원천 페이로드에 포함하지 않는다. 다운스트림 AI가 전력값만 보고 판정하도록 하기 위한 계약이다.

## 6. 현재 E2E 시나리오 10종

| 구분 | 시나리오 | 기간 | 처리 내용 |
|---|---|---:|---|
| 활동 | `ACTIVITY_NORMAL` | 1일 | 전기포트 3회, 전자레인지 2회, 청소기 1회 |
| 활동 | `ACTIVITY_LOW` | 1일 | 12:00 전자레인지 180초 |
| 활동 | `ACTIVITY_NONE` | 1일 | 대상 가전 사용 없음, 전수 발행 |
| 활동 | `ACTIVITY_INSUFFICIENT` | 1일 | 22:47:59부터 4,321슬롯 결측, 82,079건 발행 |
| 활동 | `ACTIVITY_SESSION_MERGE` | 1일 | 인덕션 600초 2회, 중간 OFF 60초 |
| 활동 | `ACTIVITY_DURATION_CAP` | 1일 | 전기포트 7,200초 연속 가동 |
| 루틴 | `ROUTINE_CHANGED_LATER` | 28일 | 이전 21일 08:00 → 최근 7일 10:30 |
| 루틴 | `ROUTINE_CHANGED_EARLIER` | 28일 | 이전 21일 10:30 → 최근 7일 08:00 |
| 루틴 | `ROUTINE_CHANGED_WITHIN_THRESHOLD` | 28일 | 이전 21일 08:00 → 최근 7일 09:30 |

가전 이벤트 구간에는 레거시 물리 모델의 서모스탯 휴지 주기를 넣지 않는다. 선언된 ON 구간을 사용자의 한 번의 연속 사용으로 보존해야 AI가 하나의 사용 세션을 여러 조각으로 잘못 나누지 않기 때문이다.

## 7. 실행 예시

### BURST 실행

```bash
curl -X POST http://127.0.0.1:8085/api/e2e/runs \
  -H 'Content-Type: application/json' \
  -d '{
    "reference_date": "2026-09-21",
    "execution": { "mode": "BURST" },
    "households": [
      { "household_id": "H001", "scenario": "ACTIVITY_NORMAL" }
    ]
  }'
```

### 자동 안전 배속 실행

```bash
curl -X POST http://127.0.0.1:8085/api/e2e/runs \
  -H 'Content-Type: application/json' \
  -d '{
    "reference_date": "2026-09-21",
    "execution": { "mode": "ACCELERATED" },
    "households": [
      { "household_id": "H001", "scenario": "BASELINE_MICROWAVE_20D" }
    ]
  }'
```

### 명시적 배속 실행

```json
"execution": {
  "mode": "ACCELERATED",
  "speed": 100
}
```

`REALTIME`과 `BURST`에서는 `speed`를 보내면 400 오류가 발생한다.

## 8. 상태와 완료 확인

```bash
# 세션 전체
curl http://127.0.0.1:8085/api/e2e/runs/{run_id}

# 가구 상세
curl http://127.0.0.1:8085/api/e2e/runs/{run_id}/households/H001
```

정상 완료는 다음 항목으로 확인한다.

1. `state == "COMPLETED"`
2. `published_samples == planned_publish_samples`
3. `completed_days == total_days`
4. 모든 `day_results[].status == "COMPLETED"`
5. `last_error == null`

`published_samples`는 시뮬레이터의 MQTT 발행 확정 수이다. Kafka 적재 무결성까지 확인하려면 Kafka 소비 건수, 중복 `message_id`, Broker dropped counter를 별도로 대조해야 한다.

## 9. 모드 선택 기준

| 상황 | 권장 모드 | 이유 |
|---|---|---|
| 실시간 파형 시연 | `REALTIME` | 실제 시간과 같은 속도로 관찰 가능 |
| 단일 일자 빠른 검증 | `BURST` | 가장 짧은 시간에 전체 슬롯 발행 |
| 20일 기준선 생성 | 자동 `ACCELERATED` 또는 검증된 환경의 `BURST` | 큐 설정과 적재 여유 확인 필요 |
| 28일 루틴 변화 생성 | 자동 `ACCELERATED` | BURST는 Broker 큐 한계에 가까움 |
| 여러 가구 동시 실행 | 자동 `ACCELERATED` | 가구 수와 무관하게 합계 약 1,200건/초 유지 |
| MQTT 계약만 빠르게 검증 | `BURST` | Kafka 최종 적재 속도와 무관한 검증 |

정리하면, **BURST는 시간축을 압축하지 않고 대기만 제거하며**, **ACCELERATED는 가상 1초의 실제 발행 간격을 제어한다**. 시나리오는 선언 데이터를 불변 실행 계획으로 컴파일한 뒤 가구별 실행기가 1초 슬롯 단위로 처리하며, 모든 모드에서 동일한 가상 시각과 동일한 시나리오 의미를 유지한다.

## 10. 관련 코드

- `engine/schedule.py`: 시나리오 선언 모델과 실행 계획 컴파일
- `engine/schedule_runtime.py`: 가상 1초 슬롯 및 물리 계측값 생성
- `engine/schedule_executor.py`: REALTIME·ACCELERATED·BURST 페이싱과 완료 불변식
- `engine/schedule_publisher.py`: MQTT 토픽·페이로드·결정적 `message_id` 생성
- `engine/unified_catalog.py`: E2E 시나리오 10종 통합 카탈로그
- `server/e2e_manager.py`: 세션 생성, 가구별 실행기, pause/resume/stop
- `server/config.py`: 자동 안전 배속 계산
- `server/request_handler.py`: REST 요청 검증과 API 라우팅
