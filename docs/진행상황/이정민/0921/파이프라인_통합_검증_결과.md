- 검증일: 2026-09-21
- 대상 브랜치: `feature/data/collection` 작업 트리 (커밋 e49bfd9 이후 미커밋 수정 포함)
- 범위: Bronze 수집 산출물 → 전력 Silver → 일별 가전 사용 요약 → 28일 Gold 프로필 → delivery outbox → Kafka → monitoring-service 프로필 반영·위험 평가·등급·알림. 보고서 연결은 제외.

## 5. 발견 사항과 수정

### 수정한 것 (좁은 범위: 기능 연결·테스트 결함)
1. **`usage-daily` 재실행이 항상 새 버전을 만들어 Gold 재사용을 깨뜨림** — `power-silver run`·`gold-profile run`은 같은 입력을 재사용하지만 `run_analysis_daily`는 무조건 새 run을 발행해, `gold-profile daily`를 같은 날짜에 반복하면 Gold 입력 스냅샷이 바뀌고 동일 데이터로 새 프로필 revision·outbox 행·Kafka 메시지가 매번 생겼다(catch-up 3일 × 매일). README·러너 주석의 "완료 단계는 manifest를 재사용" 약속과 어긋남. `analysis_job.py`에 같은 전력 스냅샷·receipt/세션 토큰·규칙·완료 정책(run details의 `analysis_policy_digest`)일 때 확정 manifest(`reused_run_id`)를 돌려주는 재사용과 `--force`를 추가. 신규 `test_analysis_job.py`, e2e T3로 검증.
2. **격리 테스트 시각 결함** — `RiskAssessmentIsolationTest`가 이벤트 등급을 고정 시각(12:10 KST)으로 심고 스케줄러는 벽시계로 평가해, 18:10 KST 이후 실행하면 6시간 유지시간이 지나 해제되어 실패. 스케줄러 경로 테스트는 벽시계로 심도록 수정.
3. **Spark 픽스처 결함** — `test_job_spark.py`가 모든 날짜에 `session-1` v1을 재사용해 logical-use 단계가 "conflicting session slice"로 거절(테스트 2건 실패). 날짜별 세션 ID로 수정. `test_analysis_coverage.py`는 naive UTC vs aware datetime 비교로 실패 → 정규화.
4. **catch-up 러너가 오래된 날짜의 INPUT_INCOMPLETE에서 멈춤** — `run-gold-daily.sh`가 exit 10에서 즉시 종료해, 예를 들어 3주 전 Silver가 비어 있으면 매일 어제 프로필이 만들어지지 않았다. 날짜별 창은 독립이므로 계속 진행하고 마지막에 10으로 종료(systemd에는 여전히 비성공으로 보임). 테스트 추가.
5. 문서: README의 `time_bucket` 예시(`"09:00-09:30"` → 실제 `"09:30"`), 재사용·러너 동작, 계약 픽스처 위치 보완.

### 수정하지 않은 것 (담당 범위·근거 명시)
- **P1-1 alembic 중복 revision (담당: ai/realtime-analysis-service)** — `20260921_15_selected_scene_evidence.py`(커밋 7e85561)와 `20260921_15_set_inactivity_threshold_one_minute.py`(293c6d5), `20260921_16_scene_events.py`(7e97353)와 `20260921_16_set_appliance_use_limits_two_minutes.py`(d0600ae)가 같은 revision ID를 선언한다. `alembic upgrade head`가 "Multiple head revisions"로 실패해 로컬 `realtime-analysis-service`가 재시작 루프 중이며, 새 compose 의존성(`gold-profile`·`power-silver`·`gold-profile-publisher` → `realtime-analysis-service: service_healthy`) 때문에 `docker compose run gold-profile`(--no-deps 없이)이 기동되지 않는다. 운영 DB에 이미 어느 쪽 15/16이 적용됐는지에 따라 rename 방식이 달라지므로 ai 파트가 두 체인을 하나로 정리해야 한다. 러너는 `--no-deps`라 타이머 경로는 이 의존성에 막히지 않지만 마이그레이션 자체가 안 되면 `gold_profile_delivery_outbox` 이후 테이블이 새 환경에 생성되지 않는다.

- Spark 스위트: `docker build --target test` (gold: `--build-context analysis=… --build-context silver=…`).
- PG 잠금: `MONITORING_PG_URL=jdbc:postgresql://localhost:55433/monitoring_db ./gradlew test --tests '*RiskAssessmentLockPostgresTest'` (일회용 postgres).
- 종단 e2e: `tests/test_e2e_local_pipeline.py` 모듈 docstring의 `GOLD_E2E_*` 환경변수로 `nilm-gold-profile:test` 컨테이너를 `nilm-net`에서 실행.
