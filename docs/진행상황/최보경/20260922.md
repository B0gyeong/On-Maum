## 요약

기존 FakePredictor 기반 실시간 분석 서비스에 NILM R3 실제 모델 6종을 연결했다.
각 가전 체크포인트를 하나의 실시간 Predictor 계약으로 묶고, 모델별 정규화·ON/OFF 임계값과
확정 샘플 수를 실제 프로파일에서 사용하도록 변경했다. 모델 자산은 시작 시 SHA-256과 실제
forward로 검증하며, 실제 모델 모드에서는 실패 시 FakePredictor로 대체하지 않도록 했다.

로컬 Docker 이미지는 `fake`, `real`, `selected_scene` 모드를 선택할 수 있게 분리했고 기본값을
`real`로 두었다. 반면 EC2-B 운영 설정에 실제 모델 환경변수를 즉시 강제하던 변경은 기존 배포
이미지와의 정합성을 위해 롤백했다.

성능 측정에서는 FakePredictor 기준 80가구 1Hz를 처리하려면 Consumer 4개가 필요함을 확인했다.
실제 모델 기준으로는 Consumer 1개가 약 15 msg/s까지 안정적으로 처리하고 20 msg/s부터 lag가
누적됐다. Consumer 2개는 20 msg/s, Consumer 4개는 40 msg/s를 오류와 DLQ 없이 처리했다.

## 1. 80가구 Consumer 확장 시험 완료

기존 문서에는 `80가구 × 1Hz` 시험의 Consumer 1개 결과만 기록돼 있었다. 이후 2개와 4개까지
측정을 완료하고, 처리 한계를 더 정확히 확인하기 위해 4·5·6개도 비교했다.

### 1.1 Consumer 1·2·4개 비교

측정 결과: `load-test-results/20260921-135613`

| Consumers | Input | Throughput | Max lag | Lag recovery | E2E p95 | CPU | RSS |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 79.59 msg/s | 20.71 msg/s | 29,887 | 1,425.63s | ≥300s | 0.59 cores | 131.58 MiB |
| 2 | 80.58 msg/s | 48.36 msg/s | 6,810 | 193.31s | 110.53s | 1.16 cores | 196.38 MiB |
| 4 | 80.36 msg/s | 75.31 msg/s | 1,070 | 58.10s | 40.09s | 2.06 cores | 366.38 MiB |

- Consumer 수에 따라 처리량은 `20.71 → 48.36 → 75.31 msg/s`로 증가했다.
- 4개에서도 측정 평균은 입력보다 약간 낮았지만, 1·2개보다 lag와 회복 시간이 크게 줄었다.
- 오류와 DLQ는 모든 조건에서 0이었다.
- 299개 warm-up은 Consumer 수가 아니라 가구별 1Hz 입력 속도의 영향을 받아 2·4개 모두 약
  320초가 걸렸다.

### 1.2 Consumer 4·5·6개 비교

측정 결과: `load-test-results/20260921-151455`

| Consumers | Throughput | Max lag | E2E p95 | Errors | CPU | RSS |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 79.91 msg/s | 46 | 945.25ms | ClockSkew 7 | 1.47 cores | 364.61 MiB |
| 5 | 79.94 msg/s | 37 | 936.83ms | 0 | 1.69 cores | 450.32 MiB |
| 6 | 79.89 msg/s | 48 | 913.98ms | 0 | 1.76 cores | 535.23 MiB |

Consumer 4개부터 입력 약 80 msg/s를 전부 처리했다. 5·6개로 늘려도 처리량과 E2E는 거의
개선되지 않았고 메모리만 증가했다. 따라서 FakePredictor와 80 msg/s 조건에서는 Consumer 4개가
비용 대비 적절하다. 4개 조건의 ClockSkew 7건은 처리 실패나 DLQ가 아니라 호스트와 Docker
시계 차이가 설정된 100ms 허용 범위를 넘은 측정 오차다.

## 2. 실제 NILM 모델 6종 실시간 추론 연결

기존 `FakePredictor` 교체 지점을 이용해 `RealtimeModelPredictor`를 구현했다.

### 2.1 실제 모델 계약

- 입력: 가구별 최근 255초의 원본 `P/Q/PF/I`
- 출력 순서: `KETTLE`, `INDUCTION`, `IRON`, `MICROWAVE`, `HAIR_DRYER`, `VACUUM_CLEANER`
- 구조: 가전별 독립 체크포인트 6개를 실행한 뒤 기존 6종 Predictor 출력 계약으로 결합
- 정규화: 각 모델 내부 프로파일의 mean/std로 정확히 한 번 수행
- 상태 판정: 프로파일별 ON/OFF threshold와 공통 confirmation sample 적용
- 모델 버전: 체크포인트 6개의 SHA-256을 조합해 결정적으로 생성

실제 모델은 자체 정규화와 threshold를 사용하므로 기존 FakePredictor용
`StandardizingPredictor`와 임시 manifest threshold를 거치지 않는다. 체크포인트 하나라도
로딩 또는 추론에 실패하면 fake 결과로 대체하지 않고 서비스 시작 또는 처리를 실패시킨다.

### 2.2 기존 파이프라인 유지

Predictor만 실제 구현체로 교체하고 다음 흐름은 그대로 유지했다.

```text
power.raw.v1
  → 가구별 255개 버퍼
  → 실제 모델 6종 추론
  → 가전별 ON/OFF 판정 및 상태 전이
  → appliance_usage_session 저장
  → 이상 패턴 판단
  → analysis.snapshot.v1 / analysis.event.v1 발행
```

가전별 OFF threshold를 상태 전이기에 직접 전달할 수 있도록 확장했고, 실제 모델의 confirmation
횟수를 ON/OFF 전이에 공통 적용했다. 기존 fake 모드는 종전 manifest와 확인 샘플 설정을 계속
사용한다.

관련 커밋:

```text

```

## 3. 모델 자산 검증과 Docker 실행 모드 분리

### 3.1 Fail-closed 자산 검증

실제 모델 이미지는 시작 전에 다음 항목을 검사한다.

- 체크포인트·정규화 파일·모델 코드 SHA-256 일치
- 6개 프로파일의 가전 순서와 255개 입력 창 일치
- 실제 모델을 로드한 뒤 각 가전에 대해 forward 수행
- 출력 shape와 유한한 확률값 확인

자산 검증이나 forward가 실패하면 서비스가 시작되지 않는다. 실제 모델 모드가 조용히 fake
모드로 바뀌는 경로는 두지 않았다.

### 3.2 이미지 target

| Target | 용도 | 허용 모드 |
| --- | --- | --- |
| `local-inference` | 로컬 개발·비교 | `fake`, `real`, `selected_scene` |
| `realtime-inference` | 실제 6종 모델 운영 이미지 | `real`만 허용 |
| `inference` | 선택 장면 검증 | `selected_scene` |

로컬 Compose는 `local-inference` target을 사용하며 기본 `MODEL_BACKEND=real`,
`MODEL_WINDOW_SIZE=255`다. 환경변수만 바꿔 fake 또는 선택 장면 모드로 전환할 수 있다.

EC2-B Compose에 `MODEL_BACKEND=real`, 자산 경로와 255개 window를 강제로 넣었던 변경은
기존 운영 이미지 계약과 동시에 바뀌지 않도록 롤백했다. 현재 EC2-B 설정은 기존
`MODEL_WINDOW_SIZE=299` 계약을 유지하며, 실제 모델 운영 전환은 새 `realtime-inference`
이미지 배포와 환경변수 변경을 한 번에 적용해야 한다.

## 4. 실제 모델 추론 시간 계측

기존 단계별 레이턴시 로그는 전체 처리시간은 기록했지만 Predictor 호출 자체를 별도 단계로
측정하지 않았다. `MeasurementHandler`의 Predictor 실행 구간을 `inference` stage로 감싸
`stage_durations_ns.inference`와 Prometheus 단계별 지연에서 확인할 수 있게 했다.

```text
buffer_append
  → inference
  → state_decision_transition
  → activity_db
  → anomaly_detection
  → snapshot_publish_ack
```

성공한 추론뿐 아니라 Predictor 예외 시에도 `FAILED_INFERENCE` 처리 계약은 유지된다.
테스트에서는 버퍼 준비 후 Predictor가 한 번 실행되면 `inference` count가 1이고 소요 시간이
0 이상으로 기록되는 것을 검증했다.

## 5. 실제 모델 부하 시험

실제 모델 모드, 255개 입력 창에서 생성된 로컬 보고서를 기준으로 정리했다.

### 5.1 단일 Consumer 처리 한계 탐색

| 가구/입력 | Throughput | Max lag | E2E p95 | Inference p95 | CPU | RSS | 판정 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 10 / 10.00 msg/s | 9.99 msg/s | 1 | 897.19ms | 47.23ms | 0.42 | 311.03 MiB | PASS |
| 15 / 15.10 msg/s | 15.07 msg/s | 14 | 954.04ms | 47.74ms | 0.64 | 311.64 MiB | PASS |
| 20 / 20.38 msg/s | 18.14 msg/s | 383 | 28.87s | 46.89ms | 0.74 | 312.15 MiB | 처리량 부족 |

Consumer 1개의 실제 모델 추론 p95는 약 `47ms`로 안정적이었다. 전체 파이프라인은 15 msg/s까지
입력을 따라갔지만 20 msg/s에서는 처리량이 입력보다 낮아 lag와 E2E가 증가했다. 따라서 현재
환경에서 단일 Consumer의 안전 처리 구간은 약 15 msg/s 이하로 본다.

### 5.2 Consumer 수평 확장

| Consumers | 입력 | Throughput | Max lag | E2E p95 | Inference p95 | Errors/DLQ | RSS |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 10.00 msg/s | 9.99 msg/s | 1 | 897.19ms | 47.23ms | 0 / 0 | 311.03 MiB |
| 2 | 20.16 msg/s | 20.16 msg/s | 13 | 895.75ms | 45.21ms | 0 / 0 | 614.38 MiB |
| 4 | 40.35 msg/s | 40.36 msg/s | 21 | 976.61ms | 49.23ms | 0 / 0 | 1,233.48 MiB |

Consumer 2개와 4개는 각각 20 msg/s와 40 msg/s 입력을 따라갔다. 추론 p95는 45~49ms로
비슷했고 E2E p95도 약 1초 이내였다. 수평 확장 시 처리량은 거의 비례했지만 RSS도 Consumer당
약 300MiB씩 증가하므로 운영에서는 목표 입력량과 메모리를 함께 고려해야 한다.

## 6. Alembic 중복 head 정리

선택 장면 저장 스키마와 정책 변경 마이그레이션이 같은 부모 revision에서 갈라져 Alembic head가
둘이 되는 문제가 있었다. 당시 두 branch를 merge revision으로 합치고 다음 검증을 추가했다.

- revision graph에 head가 정확히 하나인지 확인
- `alembic upgrade head`가 모호하지 않게 실행되는지 확인
- 선택 장면 evidence와 scene event 스키마가 모두 최종 head에 포함되는지 확인

이후 develop 통합 과정에서 revision 순서가 직렬화됐으며 현재 체인은 다음과 같다.

```text
20260920_14
  → 20260921_15
  → 20260921_16
  → 20260921_17
  → 20260921_18 (현재 head)
```

관련 커밋:

