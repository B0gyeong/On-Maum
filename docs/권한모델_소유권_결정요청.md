# 권한 모델 정리 — 보호자 제거, 대상자 계정 연동, 남은 제약

작성: 채지현 (2026-09-21) · 대상: 백엔드·AI·프론트 전원

`device_db`와 `monitoring_db`가 "사람"을 각자 다른 모델로 들고 있어 생긴 문제 세 건이다.
1·2부는 조치했고 3부는 결정이 필요하다.

| | 내용 | 상태 |
| --- | --- | --- |
| **1부** | 보호자(GUARDIAN)가 어떤 데이터도 볼 수 없었다 → 역할 제거 | device 완료 (V8) |
| **2부** | 대상자에 계정이 없어 위험 감지해도 알림이 안 나갔다 → 대리 생성 + 초기 비밀번호 | **device 완료 · monitoring 작업 필요** |
| **3부** | 담당자를 대상자당 한 명만 배정할 수 있다 | **결정 필요** |

프론트에 영향이 가는 건 1부(보호자 초대 UI 제거)와 2부(후속 과제 — 대상자 본인 로그인)다.

## 용어 (담당자 ≠ 보호자)

| 용어 | 코드 값 | 누구 | 상태 |
| --- | --- | --- | --- |
| **대상자** | `SELF` | 모니터링 받는 본인 | 사용 중 |
| **담당자** | `STAFF` | 복지사 등 기관 직원 | 사용 중 |
| ~~보호자~~ | ~~`GUARDIAN`~~ | ~~가족·지인~~ | **제거됨 (V8)** |

가입 시 `organization` 입력 여부로 갈린다. 값이 있으면 담당자로 보고 아웃박스를 거쳐
`monitoring_db.managers`에 올린다. 없으면 `user_profiles`에만 남는다.

> 같은 사람을 층마다 다르게 부른다: 프론트 "복지담당자" / monitoring `managers` /
> device_db `relation = STAFF`. 전부 동일 인물이다.

## 1부 — 왜 제거했나 (조치 완료)

### 재현했던 문제

정상 경로로 보호자를 H001에 합류시킨 뒤 조회하면 전부 막혔다.

```
보호자 가입 → 201
대상자 본인이 GUARDIAN 초대 코드 발급 → 201
보호자가 코드 수락 → 201, relation=GUARDIAN
GET /api/auth/me → households: [{ houseId: "H001", relation: "GUARDIAN" }]   ← 여기까진 정상
```

| 엔드포인트 | 보호자 | 배정 담당자 |
| --- | --- | --- |
| `GET /api/monitoring/subjects/1/events` | **403** | 200 |
| `GET /api/monitoring/subjects/1/power-usage` | **403** | 200 |

응답: `"배정된 담당자만 대상자 정보를 조회할 수 있습니다."`

### 원인

`monitoring`에는 **GUARDIAN 개념 자체가 없고** `household_members`를 읽지도 않는다.
판정은 `SubjectAccessGuard`가 `subjects.manager_id` 하나로만 한다.

```java
if (authSub.equals(subject.getAuthSub())) return subject;   // 대상자 본인
boolean assignedManager = managers.findByAuthSub(authSub)
        .map(m -> Objects.equals(m.getId(), subject.getManagerId()))
        .orElse(false);                                      // 배정된 담당자 한 명
if (!assignedManager) throw ... FORBIDDEN;
```

보호자는 `managers`에 없으므로 `findByAuthSub`가 비고 곧바로 403이다.

### 조치 (V8__remove_guardian_relation.sql)

- 미사용 GUARDIAN 초대 삭제, 사용 이력 있는 초대는 `STAFF`로 승계
- GUARDIAN 멤버십 삭제 — 어차피 어떤 조회도 통과하지 못했으므로 잃는 접근 권한이 없다.
  기관 소속이 아닌 사람에게 담당자 권한을 줄 수는 없으므로 STAFF 승격은 하지 않았다
- `household_members` · `household_invites` 체크 제약에서 `GUARDIAN` 제외
- `relation` 컬럼의 기본값(`GUARDIAN`) 제거 — **SELF와 STAFF 사이에는 합리적 기본값이 없다.**
  조용히 한쪽으로 정해지면 권한이 잘못 부여되므로 엔티티에서도 명시를 요구하도록 바꿨다

적용 확인: `household_members` STAFF 2 / SELF 10, GUARDIAN 0. 제약 위반 삽입 시도 → 거부됨.
단위 테스트 57건 통과.

## 2부 — 대상자 계정·응답 경로 (device 완료 · monitoring 작업 필요)

### 문제 — 위험을 감지해도 알림이 안 나간다

`SubjectRegistrationService.register()`가 `auth_sub`를 채우지 않는다.
`Subject` 생성자에 자리가 아예 없다.

```java
Subject subject = new Subject(
    householdId, name, birthDate, phone, address,
    addressDetail, managerMemo, manager.getId());   // ← auth_sub 없음
```

그런데 알림 경로 두 곳 모두 `auth_sub`가 없으면 **알림을 만들지 않고 빠져나간다.**

```java
// AnalysisEventService:145, RiskAssessmentService:237 — 동일
if (subject.getAuthSub() == null || subject.getAuthSub().isBlank()) {
    log.warn("이벤트 저장 완료, 수신자 식별자 없음: subjectId={}", subject.getId());
    return;
}
```

**즉 등록 API로 만든 대상자는 위험이 감지돼도 아무에게도 알림이 가지 않고 로그만 남는다.**
지금 동작하는 건 `SubjectInitializer`가 만든 테스트 데이터뿐이다 — 이쪽은 계정을 만들어
raw SQL로 `auth_sub`를 꽂는다.

> `subjects.auth_sub`가 nullable인 것은 "계정 없는 대상자를 허용하는 설계"가 아니라
> **채우는 경로를 아직 안 만든 상태**로 보는 것이 맞다. `notifications.auth_sub`,
> `push_subscriptions.auth_sub`, `managers.auth_sub`는 모두 `NOT NULL`이다.

### device 쪽 조치 (완료)

**`POST /api/auth/users`** — 담당자가 대상자 몫으로 신원만 만든다.

```
요청  Authorization: Bearer <담당자 토큰>
      { "displayName": "박어르신", "phone": "010-2222-3333", "email": null }

응답 201
      { "userId": "5476c5aa-3932-4712-8fa1-d9629b58b112",
        "email": "subject-db7ce740-7fa@no-email.nilm.local",
        "displayName": "박어르신", "phone": "010-2222-3333",
        "organization": null, "status": "ACTIVE" }
```

| 항목 | 규격 |
| --- | --- |
| 인증 | 기관 소속(`organization`) 계정만. 아니면 `403 FORBIDDEN` |
| 비밀번호 | **만들지 않는다.** 로그인 불가(`400`), Keycloak 자격증명 0개 |
| `email` | 선택. 없으면 `subject-xxxx@no-email.nilm.local` 생성 |
| 중복 | 이미 있는 이메일이면 `409 DUPLICATE_RESOURCE` |
| 실패 보상 | 프로필 저장 실패 시 Keycloak 계정 삭제 |

비밀번호를 대신 정하지 않는 이유는 **그 값을 누가 보관할지가 문제가 되기 때문이다.**
알림 수신자 식별에는 UUID만 있으면 되고, 실제 푸시 발송은 대상자가 직접 구독할 때 열린다.

검증: 대리 생성 `201` / 그 계정 로그인 `400` / 비담당자 호출 `403` /
Keycloak 자격증명 0개. 단위 테스트 3건 포함 60건 통과.

### monitoring 쪽 필요 작업

두 군데다. **팀원 파일이라 손대지 않았다.**

```java
// 1) Subject 생성자에 authSub 추가
public Subject(String householdId, String authSub, String name, LocalDate birthDate, ...)

// 2) SubjectRegistrationService.register() — 대상자 저장 전에 신원 확보
var created = deviceClient.createProxyUser(          // POST /api/auth/users
        callerBearerToken,                            // 담당자 토큰 그대로 전달
        new ProxyUserRequest(request.name(), request.phone(), null));
Subject subject = new Subject(
        request.householdId(), created.userId().toString(), request.name(), ...);
```

`TestDataApiClient`가 이미 device-service를 호출하는 구조이므로 붙일 자리는 있다.

**실패 처리 주의** — 대리 생성은 성공했는데 `subjects` 저장이 실패하면 고아 계정이 남는다.
device 쪽 가입이 쓰는 보상 삭제와 같은 방식이 필요하거나, 최소한 로그로 남겨
운영에서 정리할 수 있어야 한다.

### 대상자 자격증명 (device 완료)

대리 생성 시 **초기 비밀번호를 함께 발급**한다. 담당자가 전달하고, 대상자가 바꾸면
`password_reset_required`가 내려간다(V9).

```
POST /api/auth/users  →  201
{ "profile": { ..., "passwordResetRequired": true },
  "initialPassword": "4Q3R-YZKX-DHFZ" }        ← 1회만 노출
```

**서버가 생성하는 이유** — 담당자가 정하면 여러 대상자에게 같은 패턴(생년월일 등)을
쓰기 쉽고, 바꿨는지 추적할 수 없다. 형식은 초대 코드와 같은 알파벳(`0/O`, `1/I/L` 제외)
12자리를 네 글자씩 끊는다. **담당자가 구두·서면으로 전달해야 하므로 불러줄 수 있어야 한다.**

**Keycloak `temporary=true`는 쓸 수 없다.** 실측했다 — `UPDATE_PASSWORD` 필수 조치가
걸리면 password grant 로그인이 `"Account is not fully set up"`으로 실패한다.
직접 승인 방식에는 그 조치를 처리할 화면이 없다. 그래서 Keycloak에는 정상 비밀번호로
넣고 변경 유도는 서비스가 플래그로 한다.

검증: 발급 → 로그인 → 플래그 `true` → 변경 `204` → 플래그 `false` → 옛 비밀번호 `400`.

### 알림 응답 — 일회용 토큰 (monitoring 작업 필요)

**문제.** 세션이 짧다. 실측값은 access token 5분, **유휴 30분, 최대 10시간**이고
`rememberMe`는 꺼져 있다. 어르신 폰은 평소에 앱을 열지 않으므로
**위험 알림을 받은 순간엔 거의 항상 로그아웃 상태**다.

푸시 알림 자체는 로그인과 무관하게 도착한다(구독은 브라우저와 푸시 서비스 사이의 것).
문제는 응답이다. 지금 구조라면 **위급 상황에 어르신에게 로그인을 요구**하게 되고,
비밀번호를 기억 못 하면 무응답으로 처리되어 담당자가 헛걸음한다.

**해법 — 알림에 일회용 토큰을 담는다.** 새 토큰 체계를 만들 필요는 없다.
일회용이라 어차피 DB에 사용 여부를 남겨야 하므로 **난수 자체가 곧 보안**이고,
이건 초대 코드에서 이미 검증한 패턴이다.

| 초대 코드 | 응답 토큰 | 상태 |
| --- | --- | --- |
| `code` | `response_token` | **신규 컬럼 1개** |
| `expires_at` | `response_deadline` | 이미 있음 |
| `used_at` | `responded_at` | 이미 있음 |
| `used_by` | `auth_sub` | 이미 있음 |

**토큰은 신원을 담지 않는다.** 이미 `auth_sub`가 적혀 있는 알림 행을 가리키는 열쇠일 뿐이다.
신원이 확정되는 시점은 응답할 때가 아니라 **알림을 만들 때**다.

```
분석: H001 무활동  →  subjects(household_id='H001')  →  notifications.auth_sub 확정
                                                         response_token = hash(난수)
                                                              │
                                        푸시 → 대상자 폰 (그 사람의 구독으로만 감)
                                                              │
                          탭 → POST /respond {token} → 토큰으로 행 조회 → auth_sub가 응답자
```

**작업량** — monitoring: 마이그레이션 1개(컬럼 1), 토큰 발급 ~10줄, 응답 엔드포인트 ~40줄,
permitAll 1줄. 프론트: 라우트 1개. **게이트웨이는 이미 열어 두었다.**
기존 `NotificationService.respond()`의 중복 응답·상태 전이 로직은 그대로 쓰고
인증 부분 10줄만 갈아끼우면 된다.

**설계 시 지킬 것 세 가지**

- **토큰은 해시로 저장한다.** DB가 유출돼도 링크를 재구성할 수 없다
- **권한을 응답 하나로 좁힌다.** 토큰으로 할 수 있는 일은 그 알림에 예/아니오를 기록하는
  것뿐이어야 한다. 조회·다른 알림 접근은 막는다. 유출돼도 피해가 "남이 대신 괜찮다고 답함"에 그친다
- **수명은 `response_deadline`을 그대로 쓴다.** 별도 만료를 둘 이유가 없다

**남는 위험과 맞바꿈** — 토큰 방식의 신뢰는 "폰을 가진 사람 = 대상자"라는 가정 위에 있다.
가족이 대신 응답할 수 있다. 로그인 방식이면 신원이 더 확실하지만 응답률이 떨어진다.
**안부 확인에서는 응답률이 더 중요하다는 판단**이며, 이 맞바꿈은 의도된 것이다.
`password_reset_required`가 켜진 동안의 응답은 담당자 대리 가능성이 있으므로
감사 시 구분 근거로 쓸 수 있다.

### 아직 정해지지 않은 것 — 폰이 없는 대상자

지금 설계는 "어르신 폰이 있다"를 전제한다. 없으면 응답 단계가 통째로 빠지고
**무응답으로만 처리**되어 담당자가 매번 전화해야 한다.

기존 모델은 이 경우를 구분하지 않는다 — **"응답 안 함"과 "응답할 수단이 없음"이
똑같이 `EXPIRED`**다. 대상자 대부분이 후자라면 응답 단계를 건너뛰고 바로 담당자에게
보내는 편이 낫다. **기획에 물어야 할 질문: 어르신 몇 %가 스마트폰으로 응답할 수 있다고 보는가.**

## 3부 — 남은 제약 (결정 필요)

보호자를 걷어내도 **담당자 쪽 제약은 그대로 남는다.**

`subjects.manager_id`는 컬럼 하나라 **대상자 한 명에 담당자 한 명**만 배정할 수 있다.
구조적으로 두 명을 담을 수 없다.

### 언제 문제가 되나

- 담당 복지사가 휴가·퇴사할 때 대체 인력이 볼 수 없다
- 야간·주말 당직 담당자에게 넘길 수 없다
- 한 어르신을 두 기관(주민센터 + 복지관)이 함께 보는 경우를 표현할 수 없다

지금 시연 시나리오(담당자 1명 : 대상자 N명)는 정상 동작하므로 **급하지는 않다.**

### 선택지

**A. 그대로 둔다.** 1:1 배정이 기획 의도라면 아무것도 할 필요 없다. 다만
`household_members`의 N:M 모델과 뜻이 겹치므로 **device_db 쪽을 담당자 배정의 원본으로
쓰지 않는다는 점을 계약 문서에 명시**해야 한다. 지금은 양쪽 다 권한의 원본처럼 보인다.

**B. monitoring에 배정 테이블을 만든다.** `subjects.manager_id`를
`subject_assignments(subject_id, manager_auth_sub)`로 바꿔 N:M을 지원한다.
monitoring 안에서 끝나므로 서비스 간 계약 변경이 없다.

**C. device_db를 권한의 원본으로 삼고 이벤트로 잇는다.** 멤버십 변경 시
담당자 가입과 같은 아웃박스 방식으로 발행(`device.household-membership-changed.v1`)하고,
monitoring이 자기 읽기 모델을 채운다. 판정은 monitoring이 로컬에서 하므로
device-service가 죽어도 조회는 계속된다.

보호자가 없는 지금은 **B로 충분하다.** C는 device_db의 멤버십을 권한의 원본으로 승격하는
큰 변경인데, 지금은 담당자만 있으므로 그만한 값을 하지 못한다.
**나중에 보호자를 되살린다면 그때 C가 답이 된다.**

## 합의 절차 제안

**1단계 — monitoring 연동 (2부, 가장 급하다)**
대상자 등록 시 `POST /api/auth/users`를 호출해 `auth_sub`를 채운다.
**이게 없으면 등록 API로 만든 대상자는 위험이 감지돼도 알림이 안 나간다.**
지금 테스트 데이터로만 가려져 있는 상태다. 논의보다 구현이 먼저다.

**2단계 — 기획 확인 (1부·3부)**
안건 둘을 기획에 묻는다. 기술 논의보다 앞선다.

- **"보호자(가족·지인)가 대상자 데이터를 봐야 하는가?"** — 기획서에는 있었으나 구현이
  절반이라 일단 제거했다. 필요하다면 되살려야 하고, 그때는 두 서비스 권한 모델을 함께 설계한다
- **"대상자 한 명을 담당자 여러 명이 봐야 하는가?"** — 아니오면 3부는 A로 끝난다

**3단계 — monitoring 담당자 확인**
`manager_id` 1:N이 **의도한 제약인지, 아직 확장 안 한 것인지** 확인이 필요하다.
의도된 설계라면 그 이유가 있을 테고 논의의 전제가 바뀐다.

**4단계 — 결정 후 즉시 계약 문서화**
선택한 안을 `docs/파트간_계약_초안.md`에 추가한다. 최소한 이 두 가지:
**각 서비스가 소유하는 테이블**과 **판정 책임의 경계**. 지금은 이게 없어서
양쪽이 각자 권한 모델을 키웠다.

## 지금 알아둘 것

- **시연 시나리오는 영향 없다.** 담당자 1명이 대상자를 보는 흐름은 정상 동작한다.
  테스트 데이터가 `auth_sub`를 채워 주기 때문이며, **2부가 가려져 있는 이유도 이것이다**
- **등록 API로 대상자를 새로 만들면 알림이 안 간다.** 2부가 붙기 전까지는
  시연에서 대상자를 즉석 등록하지 말 것. 테스트 데이터로만 시연한다
- **프론트에 보호자 초대 UI가 있다면 제거해야 한다.** 이제 서버가 `GUARDIAN`을 거부한다
  (`400 VALIDATION_ERROR`). 초대 코드 기능 자체는 살아 있고 `STAFF` 초대에 쓴다
- 중간평가에서 질문받으면 "보호자는 권한 모델 통합 전까지 제거했다"가 정확한 답이다
