# 실시간 NILM 분석 Consumer, 메시지당 처리 시간 61ms → 43ms

> 프로젝트: On마음 (SSAFY 특화 프로젝트, 가구 전력 데이터 기반 생활 이상 감지)  
> 역할: AI·Backend — 실시간 분석 서비스(`realtime-analysis-service`) 담당  
> 기간: 2026-09-14 ~ 10-01 (계측 1차 → 병목 분석 → 개선 → 전후 검증)  
> 기술: Python, Kafka(confluent-kafka, cooperative-sticky), PostgreSQL(SQLAlchemy), PyTorch TCN ×6, Prometheus, Docker Compose  
> 상세 기록: `20260914_단계별_레이턴시_1차_측정.md`, `20260924_Consumer_부하_한계_탐색_및_다음_단계.md`, `20260927_observation_db_배치_flush_전후_측정.md`

## 한눈에 보기

| 지표 (1 Consumer, 20가구 × 1Hz, 600초, seed 42·43 평균) | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| 메시지당 직렬 처리 시간 | 61.4 ms | **42.9 ms** | **−30%** |
| Consumer당 처리 상한 (1000 / 처리 시간) | 16.3 msg/s | **23.3 msg/s** | **+43%** |
| 1 Consumer 안정 입력 (lag 미누적) | 15 msg/s | **22 msg/s** | **+47%** |
| 2 Consumers 안정 입력 | 25 msg/s | **40 msg/s** | **+60%** |
| 600초 동안 쌓인 Kafka lag (20 msg/s 입력) | 2,480건 | **25건** | −99% |
| E2E p95 (센서 측정 → 분석 결과 발행) | 158 s | **1.1 s** | — |
| 처리 오류 · DLQ | 0 | 0 | 유지 |

−30% 중 코드 개선은 8.6ms(−14%), 나머지 11.7ms는 **계측으로 찾아낸 측정 환경 오염을 교정**한 것이다.
두 가지는 성질이 다르므로 아래에서 분리해서 적는다.

## 문제

Kafka Consumer 하나가 처리할 수 있는 입력이 약 15 msg/s(가구 15개)에 그쳤다. 가구 수를 늘리려면
Consumer를 그만큼 늘려야 했고, 노트북 환경에서는 4개부터 CPU 경합으로 효율이 꺾였다(5개에서는
오히려 느려짐). "Consumer를 더 늘린다"가 아니라 "메시지 하나를 더 빨리 처리한다"로 방향을 바꿔야 했다.

## 접근: 계측부터

처음부터 메시지 처리의 각 단계를 `with stage("…")` 컨텍스트로 감싸 Prometheus 히스토그램과 메시지별
구조화 로그에 남기도록 만들어 두었다. 부하 측정 도구(`consumer_load_test.py`)는 Consumer 수·가구
수·seed를 받아 컨테이너 스케일링 → warm-up 대기 → 600초 안정 구간 측정 → lag 회복 확인 →
단계별 p95·처리량·lag·CPU·RSS를 보고서로 남긴다. 모든 개선은 이 도구로 **같은 seed, 같은 조건에서
2회씩** 전후를 측정했고, 두 seed 간 차이가 1% 이내임을 재현성 근거로 썼다.

개선 전 메시지 하나(약 61ms)는 이렇게 쓰이고 있었다.

```text
inference          26.0ms  42%   TCN 모델 6개 순차 추론
activity_db        17.0ms  28%   가전 세션 상태·처리 영수증 DB 트랜잭션
anomaly_detection  12.0ms  20%   위험 이벤트 평가
observation_db      5.4ms   9%   일일 관측 샘플 수 집계 (메시지마다 SELECT FOR UPDATE + UPDATE + COMMIT)
snapshot_publish    1.0ms   2%   Kafka 발행 ACK
```

## 개선 1 — observation_db: 메시지마다 쓰던 카운트를 메모리에 누적해 5초마다 flush (−5.4ms)

`sample_count`는 "오늘 몇 건 들어왔는가"라는 카운트라 실시간으로 DB에 있을 필요가 없다.
`(가구, 날짜)` 키로 메모리에 누적하고 5초마다 한 트랜잭션으로 `UPDATE … SET sample_count =
sample_count + :n`을 날리도록 바꿨다. DB 트랜잭션은 초당 20회에서 5초당 1회로 줄었다.

정확성은 다음으로 지켰다. 재처리된 과거 샘플을 걸러내던 `updated_at` 비교는 가구·날짜를 처음 만날 때
DB에서 한 번 읽어 메모리 기준값으로 캐시한 뒤 메모리에서 수행한다(Kafka가 가구별 순서를 보장하고
파티션은 한 Consumer만 소유하므로 충분하다). 리밸런싱 **revoke**에서는 Offset이 커밋되므로 반납 전에
flush하고, **lost**에서는 Offset 커밋이 보장되지 않아 새 소유자가 같은 입력을 다시 집계하므로 flush
대신 누적값을 버려 이중 집계를 막는다. 종료 시에도 `close()` 전에 flush한다. 유실 창은 최대 5초이며
at-least-once 재처리로 회복된다.

1차 구현에서 `activity_db`가 17 → 18.3ms로 느려지는 부작용이 있었다. flush가 행마다
`SELECT … FOR UPDATE` 후 UPDATE를 수행해 같은 행을 읽는 `activity_db`와 잠금 경합이 생긴 것으로
판단하고, UPDATE 한 문장으로 바꿔 잠금 시간을 statement 실행 시간으로 줄였다. 2차 측정에서
`activity_db`는 기준선으로 돌아왔고 순이익은 3.3 → 5.7ms가 됐다. 설정 `ANALYSIS_OBSERVATION_FLUSH_SECONDS`
(0이면 기존 즉시 쓰기)를 두어 **같은 이미지에서 환경변수만으로 전후 비교**가 가능하게 했다.

## 개선 2 — activity_db: 결과가 같은 DB 왕복 두 개 제거 (−3.2ms, −19%)

`activity_db`를 하위 stage로 나눠 보니 세션 갱신 5ms, 영수증 INSERT 1ms, 나머지 8ms가 조회와
COMMIT이었다. 메시지마다 수행하던 "성공 영수증 존재 확인 SELECT"와 "다음 attempt 번호 조회 SELECT"를
한 쿼리(`max(attempt)`, `max(CASE outcome='SUCCEEDED')`)로 합쳤고, 이 트랜잭션에서 세션을 만들거나
갱신하지 않은 메시지는 "변경된 세션 조회(3테이블 JOIN)"를 건너뛰게 했다. 건너뛰는 경우 기존 결과도
빈 목록이었으므로 멱등성·레이크 outbox 계약은 그대로다.

## 발견 — anomaly_detection 12ms는 코드가 아니라 DB 설정 드리프트였다 (−11.7ms)

위험 이벤트 평가는 정책의 `evaluation_interval_seconds`(기본 60초)마다 가구별로 한 번만 돌아야
하는데, 하위 stage 계측 결과 **거의 모든 메시지**가 평가 경로를 타고 있었다. 로컬 DB의
`analysis_policy`를 확인하니 두 정책의 값이 1이었다. 시연 테스트 중 DB에 직접 넣은 값이, "없는
정책만 삽입"하는 시드 로직에 잡히지 않아 계속 남아 있었고 게이트가 최솟값을 쓰므로 1Hz 입력에서
매 메시지 DB를 3~4번 치고 있었다.

이 값은 9/21 이후 **모든 부하 측정에 섞여 있었다.** DB를 기본값으로 되돌리고, 서비스 시작 시 실제
적용되는 평가 주기를 로그로 남겨 60초 미만이면 WARNING을 내도록 추가했다. 교정 후
`anomaly_detection`은 12.0 → 0.3ms가 됐고, 이전 문서의 "Consumer당 12~15 msg/s" 결론도 이 오염을
포함한 값이었음을 기록했다. 하위 stage 계측이 없었다면 두 병목 모두 "DB가 느리다"로 뭉개졌을 것이다.

## 시도했지만 채택하지 않은 것 — PyTorch 스레드 수

`inference` 26ms를 설정만으로 줄이려 `MODEL_THREADS`를 1 → 2 → 4로 바꿔 측정했다. 2는 inference만
16% 줄고 DB 단계가 그만큼 느려져 합계가 같았고(CPU는 2배), 4는 모든 단계가 2배 느려졌다.
PostgreSQL·Kafka·Prometheus가 같은 노트북에서 도는 환경에서 스레드 병렬화는 제로섬이었다.
다음 개선은 여러 가구의 윈도우를 모델당 forward 1회로 묶는 **배치 추론**이어야 한다는 근거가 됐다.

## 결과

### 단계별 전후 (avg ms)

```text
                    개선 전     개선 후
inference            26.0   →   27.8   (변화 없음, 남은 병목 65%)
activity_db          17.0   →   13.8   (−19%, 왕복 2개 제거)
anomaly_detection    12.0   →    0.3   (설정 드리프트 교정)
observation_db        5.4   →    0.02  (인메모리 누적 + 5초 flush)
snapshot_publish      1.0   →    1.0
────────────────────────────────────
합계                 61.4   →   42.9   (−30%)
```

### 한계 곡선 (1 Consumer, D 코드)

| 입력 | Throughput | 600초 max lag | E2E p95 | 판정 |
| ---: | ---: | ---: | ---: | --- |
| 20 msg/s (×2) | 19.91 | 19~31 | 1.0~1.2 s | 안정 |
| 22 msg/s | 21.91 | 23 | 2.1 s | 안정 (여유 약 15%) |
| 23 msg/s | 21.58 | 841 | 48.9 s | 한계 초과 |

개선 전에는 15 msg/s 안정, 20 msg/s에서 lag 383(120초)·2,480(600초)으로 한계 초과였다.
2 Consumers × 40 msg/s도 lag 95 → 15로 안정이어서, 단일 Consumer 개선이 수평 확장에 그대로 전파됐다.

## 측정에서 배운 것

**같은 조건, 같은 seed, 2회.** 전후 비교는 모두 1 Consumer × 20가구 × 600초, seed 42·43으로
했고, 두 seed의 모든 지표 차이가 1% 이내였다. 그래서 5%짜리 변화도 노이즈와 구분할 수 있었다.

**순수 CPU 단계를 호스트 상태의 기준 지표로.** `inference`는 DB를 타지 않아 코드·입력량과 무관하게
일정해야 한다. 10/1에 세 런이 inference 38~41ms(정상 26~28ms)로 모든 단계가 1.5배 느려졌는데,
모두 직전 런 직후 연달아 돌린 것이었다. 노트북 발열 스로틀링으로 판단해 제외했고, 이후 런 사이에
10분 간격을 두는 규칙을 만들었다. 이 기준이 없었다면 "22가구는 한계 초과"라는 잘못된 결론을 냈을 것이다.

**도구의 PASS를 믿지 않기.** 측정 도구는 파티션·오류·DLQ만 보고 PASS를 찍었고 lag 2,570인 런도
PASS였다. 안정 여부는 max lag와 처리 상한으로 따로 판단했고, 판정에 성능 기준을 넣는 것을 도구
보완 항목으로 남겼다. 컨테이너를 재사용하면 이전 런의 warm-up 상태가 남아 측정이 끝나지 않는 문제,
히스토그램 버킷 경계(50.00ms)가 p95로 찍히는 문제도 같은 맥락에서 기록했다.

**암달의 법칙을 먼저 계산하기.** observation_db는 전체의 9%였으므로 그것만 없애서는 20 msg/s를
넘길 수 없다는 것을 시작 전에 계산했고, 판정 기준을 "안정/불안정"이 아니라 "단계 p95와 처리 상한"으로
정했다. 결과는 예측(+9%)과 일치했다. 큰 숫자는 그 뒤 계측이 찾아낸 설정 드리프트에서 나왔다.

## 남은 일

`inference` 27.8ms가 남은 43ms의 65%다. poll에서 받은 여러 가구의 윈도우를 모델당 한 번의 forward로
묶는 배치 추론이 다음 단계이며, Consumer 루프를 메시지 단위에서 배치 단위로 바꿔야 해 Offset 저장·
실패 처리·가구별 순서 보장을 함께 설계해야 한다. `activity_sessions` 5ms는 열린 세션 id를 캐시해
JOIN 없이 PK로 잠그면 2~3ms 더 줄일 수 있다. 측정 도구에는 warm-up 잔존 상태·정책 평가 주기·inference
기준치의 pre-check와 lag·E2E 성능 판정을 추가할 계획이다.
