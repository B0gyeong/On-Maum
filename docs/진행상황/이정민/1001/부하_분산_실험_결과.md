## 3. 환경과 준비

### 3.1 서버

EC2-B 1대(메모리 15 GB). Spark master 1개와 worker N개를 같은 서버의 컨테이너로 띄웠으므로 "분산"은 노드 분산이 아니라 **실행기(executor) 분산**이다. 실험 중 다른 운영 컨테이너(Kafka, PostgreSQL, HDFS, 실시간 분석, 집계)는 그대로 떠 있었다.

### 3.2 환경 정리

| 작업 | 내용 | 이유 |
|---|---|---|
| HDFS 쿼터 상향 | `/nilm` 250 GB, `/nilm/gold` 32 GB | 부하 데이터와 보고서가 기본 80 GB, 2 GB를 넘음 |
| 잔여 프로세스 정리 | Kafka 컨테이너 안 ConsoleConsumer 5개 종료 | 이틀째 남아 2 GB 점유. 가용 메모리 8.9 → 10.9 GB |

### 3.3 메모리 설정 (OOM을 겪은 뒤 확정)

| 대상 | 설정 |
|---|---|
| 드라이버 | 1.5 GB. local 비교는 4 GB, 1000가구 Gold는 6 GB |
| worker 1개 | 코어 1개, 실행기 1 GB, 데몬 256 MB, 컨테이너 상한 2.5 GB |
| 안전장치 | Spark 컨테이너 `oom-score-adj 500`, 실행 전 가용 메모리 확인, 회차당 45~60분 제한 |

### 3.4 데이터

가상 가구는 10초 간격이라 가구당 하루 8,640행이다. 1000가구 하루치 864만 행은 실제 1초 간격 가구 100곳과 같은 양이다.

```bash
/opt/nilm/experiments/load/bin/load-setup.sh 1000 && /opt/nilm/experiments/load/bin/load-write.sh 1000
```

### 3.5 스크립트 (`/opt/nilm/experiments/load/bin/`)

| 스크립트 | 역할 |
|---|---|
| `common.sh` | 이미지, 네트워크, 날짜 범위(`LOAD_FROM`, `LOAD_TO`) 공통 변수 |
| `load-setup.sh N` | 가구 N곳 시나리오와 관측 대상 파일 생성 |
| `load-write.sh N` | 가상 가구 Bronze를 HDFS에 적재. 이미 있는 날짜는 건너뜀 |
| `load-config.sh N CFG` | 구성별 전용 DB, 출력 경로, Spark 설정 생성 |
| `load-run.sh N CFG W` | `gold-experiment`로 날짜별 집계 실행과 기록 |
| `cluster.sh up W` / `down` | Spark master 1개와 worker W개 기동·제거 |
| `cluster-repeat.sh "구성" 횟수` | worker 수별 반복 실험 |
| `bench.sh "가구" "worker" "파티션" 횟수` | 규모·튜닝 반복 실험 |
| `local-repeat.sh`, `gold1000.sh` | local 모드 비교, 1000가구 Gold 측정 |

## 4. 실험별 결과

exit 10(`INPUT_INCOMPLETE`)은 실험용 창(3일)이 아직 차지 않은 날짜, exit 12(`PUBLISH_PENDING`)는 Gold 완료 후 발행 대기다. 둘 다 계산은 끝까지 돌았으므로 시간 측정에 포함했다. (2026-09-30 커밋 `cc3f8f3`부터 Kafka 발행이 사라져 12는 0으로 바뀐다.)

### 4.1 분산 실험 — worker 수

500가구, 9월 23일 하루, 셔플 파티션 200, 회차마다 새 DB.

```bash
setsid nohup /opt/nilm/experiments/load/bin/cluster-repeat.sh "3 4" 5 > /opt/nilm/experiments/load/cluster-repeat.log 2>&1 &
setsid nohup /opt/nilm/experiments/load/bin/cluster-repeat.sh "1 2" 3 > /opt/nilm/experiments/load/cluster-repeat-12.log 2>&1 &
```

| worker | 회차 | 평균 | 최소~최대 | Speedup | Efficiency | Spark CPU |
|---|---|---|---|---|---|---|
| 1 | 3 | 1,179.0초 | 1,177.8~1,179.9 | 1.00 | 100% | 118% |
| 2 | 3 | 808.0초 | 797.2~814.5 | 1.46 | 73% | 219% |
| 3 | 5 | 802.0초 | 796.7~807.6 | 1.47 | 49% | 269% |
| 4 | 5 | 822.1초 | 816.7~827.3 | 1.43 | 36% | 297% |

16회 모두 OOM 없이 완료됐다. worker 2개에서 포화되고 4개는 오히려 느려진다. Amdahl 기준 순차 구간이 약 37%로, 정제·일별 요약 단계의 파일 읽기·쓰기와 드라이버 쪽 작업이 병렬화되지 않는 부분이다.

### 4.2 규모 실험 — 가구 수

worker 3개, 파티션 200, 9월 20일 첫날(전날 데이터 없음), 각 2회.

```bash
BENCH_DATE=2026-09-20 /opt/nilm/experiments/load/bin/bench.sh "10 100 500 1000" "3" "200" 2
```

| 가구 | 클러스터 (평균) | 초당 처리 행 | local 4코어 (첫날) | 차이 |
|---|---|---|---|---|
| 10 | 225.3초 | 383 | 123.0초 | +102초 |
| 100 | 390.7초 | 2,211 | 245.1초 | +146초 |
| 500 | 824.1초 | 5,242 | 653.2초 (9/23 기준, 4.3절) | +149초 (9/23 클러스터 802.0초 대비) |
| 1000 | 1,408.6초 | 6,134 | 1,272.3초 (4 GB) / 1,215.9초 (6 GB) | +137 / +193초 |

가구 1곳당 추가 시간은 두 방식 모두 약 1.13초로 같다. 클러스터는 실행기 기동과 데이터 교환 때문에 고정 비용이 100~150초 더 든다. 이 규모에서는 단일 서버 local 모드가 유리하고, 클러스터가 이기려면 가구 수가 훨씬 커지거나 노드가 실제로 나뉘어야 한다.

## 7. 이번 코드 변경과의 관계

2026-09-30 커밋 `cc3f8f3`(브랜치 `feature/data/gold-baseline-ownership`)로 Gold가 분석 DB `routine_baseline`을 직접 쓰고 Kafka 발행 경로를 없앴다. 실험이 재는 구간(정제 → 사용 요약 → 28일 요약)은 그대로이고, 추가된 것은 마지막의 DB upsert 한 번(가구 × 가전 행, 초 단위)뿐이라 위 측정값은 바뀐 구조에서도 유효하다. 다만 `--no-publish` 옵션이 사라졌으므로, 새 이미지로 실험 스크립트를 다시 돌리려면 `load-run.sh`·`gold-experiment` 호출에서 그 옵션을 빼야 한다.

# 2부. 두 서버 분산 (EC2-A worker·datanode 추가)

- 실험일: 2026-10-01 01:48 ~ 12:41 KST (EC2-B 오케스트레이션, EC2-A 원격 조작)
- 스크립트: 저장소 `experiments/cross-host/`, 서버 `/home/ubuntu/cross-host/`. 기존 1부 스크립트는 수정하지 않았다.
- 조건: 1부 분산 실험과 동일(500가구, 9월 23일 하루, worker당 코어 1·실행기 1.2 GB·컨테이너 상한 2.5 GB, 셔플 파티션 200, 회차마다 새 DB·출력 경로). 각 시나리오 3회, 총 15회. OOM 0건.

## 1. 요약

| 결론 | 근거 |
|---|---|
| 같은 자원이면 두 서버가 한 서버보다 빠르다 | 2코어 기준 한 서버 808초, 두 서버 702초 (13% 단축) |
| datanode까지 나누면 조금 더 빠르다 | 702초 → 669초 (5% 단축). 입력이 440 MB라 효과가 작다 |
| 두 서버에서는 4코어까지 계속 빨라진다 | 4코어 490초. 1부의 단일 서버 4개(822초)보다 1.68배 빠름 |
| 1부의 "worker 2개 포화"는 서버 안 경합이 원인 | EC2-B에 Kafka·PostgreSQL·실시간 분석이 같이 떠 있어 worker를 몰면 CPU·디스크를 다툰다 |
| 재현성 좋음 | 모든 시나리오의 회차 간 편차 30초 이내 |

## 2. 구성

```text
EC2-B 172.26.12.162 (4 vCPU, 15 GB)                 EC2-A 172.26.8.92 (4 vCPU, 15 GB)
  spark-master     host 네트워크 :7077          <--  spark-worker-a1, a2 (host 네트워크)
  spark-worker-b1, b2 (host 네트워크)
  load-driver-*    compose 브리지, :7078 :7079 호스트 공개  <-- 실행기 접속
  namenode :9000 공개                             <--  datanode-a (hostname=172.26.8.92)
  datanode hostname=172.26.12.162, :9864 :9866 공개
  운영 컨테이너: Kafka, PostgreSQL, 실시간 분석, 집계, 로더 (그대로 떠 있음)
  (EC2-A 운영 컨테이너: 모니터링, 게이트웨이, Keycloak, Grafana, Jenkins — 그대로 떠 있음)
```

1부와 다른 점은 master·worker를 호스트 네트워크에 두고 사설 IP로 광고한 것, 드라이버 포트를 고정 공개한 것, datanode가 자기 hostname을 사설 IP로 광고하도록 바꾼 것이다. 다른 서버에서는 도커 브리지의 컨테이너 이름을 풀 수 없기 때문이다. 이 때문에 1부와 같은 구성(B worker 1개)도 1부보다 약 8% 느리게 측정됐다(1,179초 → 1,273초). **비교는 2부 안에서만 한다.**

## 3. 시나리오와 결과

| 시나리오 | datanode | worker (B+A) | 코어 | 평균 | 최소~최대 | baseline 대비 | 코어당 효율 |
|---|---:|---|---:|---|---|---|---|
| baseline | 1 | 1+0 | 1 | 1,272.6초 | 1,259.7~1,283.5 | 1.00 | 100% |
| worker-up | 1 | 2+0 | 2 | 808.2초 | 803.2~812.5 | 1.57 | 79% |
| spark-dist | 1 | 1+1 | 2 | 701.7초 | 687.2~719.2 | 1.81 | 91% |
| hdfs-spark | 2 | 1+1 | 2 | 669.1초 | 664.9~674.4 | 1.90 | 95% |
| scale | 2 | 2+2 | 4 | 489.8초 | 486.7~494.8 | 2.60 | 65% |

발표 흐름: 단일 서버(baseline) → 병렬성 증가(worker-up) → 서버 분산(spark-dist) → 저장소까지 분산(hdfs-spark) → 자원 확장(scale).

### 3.1 서버 분산 효과 — worker-up 대 spark-dist

총 코어가 같은 두 구성이라 순수한 "서버를 나눈 효과"다. 두 서버가 106초(13%) 빠르다. 실행기 사이의 셔플이 서버를 넘나드는 비용보다, EC2-B 한 대 안에서 worker 2개와 운영 컨테이너가 CPU·디스크를 다투는 비용이 컸다.

### 3.2 저장소 분산 효과 — spark-dist 대 hdfs-spark

A에 datanode를 추가하고 입력 Bronze를 두 노드에 복제(`setrep 2`)했다. Spark는 블록이 있는 서버의 실행기에 태스크를 우선 배정하므로 A의 실행기가 자기 서버 datanode에서 읽는 비율이 늘어난다. 33초(5%) 단축. 입력이 440 MB라 네트워크 전송 자체가 작아 효과가 제한적이다. 입력이 클수록 커질 항목이다.

### 3.3 자원 확장 — hdfs-spark 대 scale

코어 2배에 1.37배. 포화가 시작됐지만, 1부에서 단일 서버 worker 4개가 822초로 3개(802초)보다 오히려 느려졌던 것과 달리 두 서버에서는 계속 빨라진다. 1부 결론 "worker 2개에서 포화"는 알고리즘의 순차 구간보다 **한 서버 안의 자원 경합**이 더 큰 원인이었다.

### 3.4 가구 수 2배 — 1000가구 (10/1 13:38~21:43 KST)

같은 5개 시나리오를 1000가구로 반복했다(각 3회. baseline·spark-dist는 10/2 새벽 보강 1회 포함). 입력은 하루 864만 행,
Bronze 약 450 MB/일로 500가구의 2배다.

| 시나리오 | datanode | worker (B+A) | 코어 | 500가구 | 1000가구 | 배율 | 1000가구 코어당 효율 |
|---|---:|---|---:|---|---|---|---|
| baseline | 1 | 1+0 | 1 | 1,272.6초 | 2,377.1초 | 1.87 | 100% |
| worker-up | 1 | 2+0 | 2 | 808.1초 | 1,465.7초 | 1.81 | 81% |
| spark-dist | 1 | 1+1 | 2 | 701.7초 | 1,264.6초 | 1.80 | 94% |
| hdfs-spark | 2 | 1+1 | 2 | 669.1초 | 1,212.7초 | 1.81 | 98% |
| scale | 2 | 2+2 | 4 | 489.8초 | 828.2초 | 1.69 | 72% |

- **가구 수에 거의 비례한다.** 모든 구성이 1.7~1.9배로 늘어, 처리 시간은 입력 크기에 선형이다.
- **서버 분산 효과는 그대로 13%** (1,465.7 → 1,264.6초, 13.7%). 500가구의 13%와 같다. 분산으로 줄어드는 비용이
  입력에 비례하는 경합 비용이라는 뜻이다.
- **저장소 분산 효과도 비슷한 4%** (1,264.6 → 1,212.7초, 4.1%). 입력을 2배로 키워도 비율은 커지지 않았다.
  로컬리티로 아끼는 것이 읽기 시간의 일정 비율이기 때문이다. 절대값으로는 33초 → 52초.
- **확장성은 입력이 클수록 좋다.** 코어 2배에 500가구 1.37배, 1000가구 1.46배. 입력이 커질수록 고정
  비용 비중이 줄어 코어를 늘린 효과가 잘 나타난다. 1부의 단일 서버 4개(1000가구 1,408.6초)보다 1.70배 빠르다.
- 회차 간 편차는 hdfs-spark 3회차(1,240초, 다른 두 회차 1,199초)만 3% 벌어졌고 나머지는 1% 안쪽이다.
  그 회차는 백그라운드 HDFS 복제가 돌던 시간대라 영향을 받았을 수 있다.

#### 창 크기에 대한 확인

"창을 7일로 늘려 입력을 키운다"는 시도는 **효과가 없었다**(1,230초 ≈ 3일 창 1,199초). `gold-profile daily`의
창 정렬은 **이미 Silver가 있는 날짜만** 다시 집계하고 없는 날짜는 `skipped_dates`로 보고하기 때문에, 구성마다
새 출력 경로를 쓰는 실험에서는 창을 어떻게 잡아도 하루치 Silver + Gold만 처리한다. 1부·2부의 모든 회차가
exit 10(`INPUT_INCOMPLETE`)이었던 이유다. 입력을 진짜 키우려면 한 회차에서 날짜를 연속 처리해야
한다(`LOAD_FROM`~`LOAD_TO` 7일, 회차당 약 7배). 이번에는 시간 관계로 하지 않았다.

## 4. 겪은 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| 첫 스모크 실패 "All masters are unresponsive" | 이 서버들은 Lightsail이라 보안그룹이 없고 ufw가 막는다. 드라이버(도커 브리지)에서 호스트 네트워크의 master로 가는 연결을 ufw가 거부 | `ufw allow from 172.18.0.0/16`(도커 브리지 대역) 추가. 두 서버 사이는 상대 사설 IP TCP 전체 허용 |
| worker-up 3회 전부 실패 (`FetchFailedException`, `NoSuchFileException`) | 같은 서버의 worker 2개가 호스트 네트워크라 주소가 같아, Spark가 셔플 블록을 네트워크 대신 로컬 디스크에서 직접 읽으려 함. worker가 각자 컨테이너라 `/tmp`가 다름 | 드라이버에 `spark.shuffle.readHostLocalDisk=false`. 재실행 3회 정상 |
| hdfs-spark 입력 복제가 45분 동안 안 끝남 | Spark가 쓴 파일이 클라이언트 기본 복제계수 3으로 생성돼 있었음. datanode가 1개일 때는 무해했으나 2개가 되자 4.8만 블록(실험 출력 3.4만 + Gold 1.4만)이 복제 대기열에 들어가 입력 147블록이 차례를 못 받음 | `/nilm/experiments`, `/nilm/gold`를 클러스터 정책과 같은 복제계수 1로 설정(메타데이터만 변경). 입력 복제가 수 분 안에 완료 |
| run-all이 첫 시나리오 뒤 종료 | `while read`로 목록을 읽는 동안 `experiment.sh` 안의 ssh가 표준입력을 삼킴 | 목록을 배열로 먼저 읽고 `< /dev/null`로 실행 |
| spark-dist-1000 처음 2회 실패 ("No active nodes contain this block") | datanode 1개 시나리오가 A를 내리기 전에 복제계수를 1로 낮춰 namenode가 B 쪽 복제본을 지운 블록이 생김 | 순서를 "A 내림 → dead 판정 대기 → 복제계수 1"로 변경 |
| 실행 중 스크립트를 덮어써 체인이 엉뚱한 분기 실행 | bash는 스크립트를 실행하며 조금씩 읽는다. 같은 경로에 scp로 덮어쓰자 바뀐 바이트 위치를 읽음 | 중단 후 재시작. 수정본은 `.new`로 올린 뒤 `mv`로 교체(원자적) |
| 7일 창이 하루치만 처리 | 창 정렬이 Silver 없는 날짜를 건너뜀(3.4절) | 중단. 입력 확대는 날짜 연속 처리로만 가능 |
| master 생존 worker 수가 항상 0 | master UI JSON 경로가 `/json/`(끝 슬래시 필수). `/json`은 리다이렉트만 반환 | 경로 수정 |

## 6. 정리와 남은 것

- 실험 뒤 상태: A의 datanode·worker, B의 cross master, HDFS 포트 공개, ufw 임시 규칙이 남아 있다. 정리 절차는 `experiments/cross-host/README.md`. HDFS 포트 공개는 다음 Jenkins 배포가 compose.yaml을 덮어쓰면서 자동으로 원래대로 돌아간다.
- 실험 출력이 다시 복제계수 3으로 쓰여 A로 복제 대기 중인 블록이 남아 있다(운영 무해). `hdfs dfs -setrep 1 /nilm/experiments`로 한 번 더 내리면 깔끔하다. 근본 해결은 Gold·Silver 배치의 Spark 설정에 `spark.hadoop.dfs.replication=1`을 두는 것이다.
- 1000가구에서도 서버 분산 14%, 저장소 분산 4%로 비율이 비슷했다(3.4절). 전체 회차와 실패 원인은 1002 최종 보고서. 7일 이상 날짜를 연속 처리하는
  실험(회차당 2시간 이상)은 하지 않았다.
- 1부와 2부의 baseline이 8% 다르므로 보고서에서는 두 부를 섞어 비교하지 않는다.
